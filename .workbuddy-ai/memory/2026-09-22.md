## 用户体验架构诊断与重构方案（校园集市）

以用户体验架构师角色，完成了一次全链路 UX 架构诊断 + 重构方案设计。

**产出**
- `campus-market-frontend/docs/ux-architecture-redesign.md`（完整方案）

**诊断结论**：断点在「信息架构」与「交易闭环」两层，视觉层无需改动。

**6 个断点**
1. P0 首屏是 Hero 发布会叙事，`#marketplace` 集市被压到第 3 屏
2. P0 无独立搜索页 / 分类页 / 求购入口（搜索直接 `/?keyword=`）
3. P0 下单链路断裂：`ProductDetailPage.submitBooking()` 提交后直接 `navigate('/profile/orders')`，无确认页、无成功页、无金额确认
4. P1 无订单详情页，确认码/状态推进/评价全挤在 `OrdersPage` 列表卡片；下单不建会话，沟通与订单脱节
5. P1 评价入口弱；收藏无降价提醒
6. P1 动作触发的登录跳转绕过回跳机制：`RequireAuth`/`LoginPage` 的 `from` 机制是完整的，但 `Navbar.handlePublish/handleMessages`、`BottomNav.handleClick`、`HomePage.goToPublish` 用裸 `navigate('/login')` 不带 `from`

**重构主线**：首屏任务归位 / 交易闭环补全（详情→确认页→成功页→订单详情页）/ 订单与沟通合流（下单即建会话 + 订单卡片置顶）

**新增路由**：`/search` `/category/:slug` `/checkout/:productId` `/checkout/:productId/success` `/orders` `/orders/:id` `/wanted` `/notifications` `/user/:id`

**架构级发现**：`MarketContext.tsx` 循环 `listProducts({pageSize:100})` 把全量商品拉进内存做前端过滤，且 `setInterval` 15s 全量轮询 —— 商品量上千后会拖垮首屏。建议拆 Context + 分页 + 服务端筛选。

**后端待补**：users 信用字段（成交数/好评率/认证状态）；conversations 支持 `order` 类型消息。

## 首页 Hero 滚动叙事改造（UI 设计）

以 UI 设计师角色，针对「首页 Hero 向下滑动太单调」完成诊断 + 设计 + 高保真原型。

**产出**
- `campus-market-frontend/docs/hero-redesign/prototype.html`（单文件高保真原型）
- `campus-market-frontend/docs/hero-redesign/hero-scroll-redesign-spec.md`（设计规范）

**诊断（实测证据）**：`index.css:193` 把 `.cm-apple-hero-stage` 拉到 180vh，`index.css:228` 容器 sticky 钉死，而 `HomePage.tsx:117-131` 的 180vh 行程只驱动 ±50px 位移 + 一次淡出 → **滚动零信息增量**。
附带发现 3 个真实缺陷：① 首屏主 CTA 被裁出视口（P0）；② 标题 `clamp(3.2rem,6.4vw,5.8rem)` 在 1080px 下孤字成行；③ 滚动进度条永远不可见。

**方案**：舞台 180vh→300vh，切为三幕（宣言 0–0.33 / 展台 0.28–0.68 / 入场 0.62–1.0）。
- 文案用带位移的交叉淡入淡出，卡片用 `--fan` 连续插值（文字阶梯、物件连续）
- 关键边界：侧卡缩放必须降到 0.68、展台宽 360px 居中，扇形外延 266px 才不溢出视口（实测）
- 去掉 `preserve-3d`：中卡 `translateZ` 会导致背面卡价签 3D 排序穿透，改纯 z-index
- 数据计数从 1,200 起跳而非 0（避免首屏出现「0 件好物在线」）

**验证**：1440×900 / 390×844 / reduced-motion 三档逐帧截图；`elementFromPoint` 与 `getBoundingClientRect` 定量核验；右侧溢出 0px、无控制台报错。

**与既有 UX 架构方案的关系**：不冲突，是前置步骤。架构方案主张 Hero 后移折叠；本方案先把 Hero 改成值得看的三幕 + 终章 CTA 主动交接。推荐路径 A（保留 Hero），因为改造后首屏 CTA 已可见。

## 工具经验（可复用）

- **并行编辑同一文件会丢更新**：同一消息里发多个 Edit 作用于同一文件，后写的会覆盖先写的（读-改-写竞态）。本次 8 处修改只落盘了 4 处。**正确做法：用一次性脚本原子化批量替换，并对每处 `assert count == 1` 校验。**
- **`agent-browser open` 打开 `file://` 会走缓存**，改了文件但看到旧样式。必须加 `?v=N` 破缓存，并用 `getComputedStyle` 校验关键值确认加载的是新版本。
- 滚动驱动型 UI 的核验方法：`set viewport` → `scrollTo` → `wait`（等 lerp 收敛）→ `screenshot`，配合 `getBoundingClientRect` / `elementFromPoint` 做定量断言，比肉眼看截图可靠。

## 功能创新机会（用户体验架构师续篇）

在 UX 架构方案中追加「第 9 章 功能创新机会」（同一文件 `docs/ux-architecture-redesign.md`）。

**核心判断标准**：这个功能，闲鱼能不能抄走？能抄的只是功能，抄不走的才是壁垒。校园平台唯一独有的三层密度：**课程表、宿舍楼、班级群**。

**三重校园密度模型**
- 课程密度（时间轴上的同一门课）→ 课程教材图谱 / 学期轮回匹配 / 按课程代码搜索
- 空间密度（同一栋宿舍楼）→ 楼栋集市 / 面交档期握手 / 出发·已到同步
- 关系密度（班级·社团·宿舍群）→ 圈子集市 / 班级代发布

**8 项创新清单**（含数据模型）
1. 楼栋集市 — `products.building`
2. 课程教材图谱 — `courses` + `course_textbooks`
3. 学期轮回匹配 — 依赖课程图谱
4. 面交档期握手 — `meeting_points.popular_slots`，时间由单值改时段多选求交集
5. 出发·已到同步 — `orders.buyer_eta_state/seller_eta_state`（明确不做实时位置）
6. 圈子集市 — `products.visibility` + `circles`
7. 班级代发布 — `publisher_id` 与 `owner_id` 分离
8. 结构化验货清单 — `orders.inspection_checklist`

**关键洞察（值得记住）**
- **需求雷达**是「求购池」的升级：从「发帖等人看」改为「订阅 + 排队」，且商品上架时**同步**触发匹配，而非等定时任务。这是「上架即命中」与「发帖石沉大海」的分水岭。
- **结构化验货清单**是合规前提下的信任替代：因为方案明确不接平台支付（无法用资金担保），所以只能**担保验货过程**——把口头验货变成结构化勾选凭证。这是唯一能补上「信任担保」的位置。

**优先级**：楼栋集市（成本最低、直接打成交率）> 需求雷达+排队（打冷启动）> 课程教材图谱（壁垒最高）

**明确不做**：AI 识真、自制担保支付、社区动态/直播、实时位置、积分提现。

## 盈利模型（用户体验架构师续篇二）

在 UX 架构方案中追加「第 10 章 盈利模型」（同一文件）。明确**细化而非替换** `方案设计.md` 第九章。

**先排除的答案**：交易佣金永远不做。测算：校园二手 AOV ¥30–80，单用户年成交 3–8 次，抽 5% = 每单 ¥1.5–4 → 覆盖不了支付+纠纷成本，且必然驱使绕开平台走微信。

**三个付费方**
- 校园商户 → 为「获客」付钱（认证商家月费 / 服务线索费 / 券核销服务费）
- 学生用户 → 为「省时间·降风险」付钱（官方验机 / 校园跑腿 / 清仓推广包）
- 平台自身 → 从「回收差价」赚钱（整间宿舍打包回收 / 专业回收转售）

**单校区稳态测算**（5000 学生 / 30% 渗透）：平月 ≈ ¥6,200，毕业季月 ≈ ¥9,800，年化 ≈ ¥8 万/校区。

**核心洞察（最重要，值得记住）**
1. **商户侧的收费门槛远低于用户侧**。商户买的是「这里有多少学生」（用户规模），不是「这里成交多少单」（交易密度）→ 活跃用户过千即可启动商户侧变现；增值服务必须等交易密度成立。
2. **商品密度不足时向用户收费会直接杀死流动性**。用户侧收费的前提是「平台已经帮他成交过」。
3. **规模来自校数，不来自单校深度**。单校区天花板仅 ¥8 万/年 → 推导出三条硬约束：模型必须可复制 / 不能做依赖大量人工审核的功能 / 必须有校园运营官体系（学生代理做 BD）。这三条反过来约束产品设计。

**变现解锁阶梯**
- 用户规模起来（活跃 ≥1000）→ 商户侧
- 交易密度起来（在售 ≥300 件 · 周成交 ≥30 单）→ 增值服务
- 运营成熟（稳态月收入 ≥¥5,000）→ 自营回收 + 多校复制

**结论**：7 项收入全部依赖未开发功能 → **当前阶段不应考虑盈利**，资源全部投入 P0 断点修复与商品密度。
