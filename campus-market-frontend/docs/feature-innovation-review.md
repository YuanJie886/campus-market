# 校园集市 · 功能创新评审与补充

日期：2026-09-22。评审对象：用户提供的 `feature-innovation.md`。本文是讨论稿，补充方案与实施边界，不表示功能已实现，也不自动修改需求基线。

## 1. 总体结论

方向合理：围绕同校供需、近距离面交和教材版本组织产品，比堆叠通用功能更聚焦。但原方案将竞争壁垒、产品假设和实现成本写得过于确定，建议先用单校试点验证。

判断标准应从“闲鱼能不能抄”改为：是否存在高频痛点、能否改善成交、数据能否持续维护、运营成本是否可承担。课程、空间、关系是有用的分析框架，但不是校园创新的全部，也不是天然独占资产。

真正可能积累的优势是：持续有效的本校供给、经核验的教材关系、稳定的交付体验及本地运营能力。原文关于竞争对手“拿不到”“无法使用”等结论缺乏证据，应改为待验证的差异化假设。

## 2. 原方案需要修正的地方

| 原设计 | 评审与建议 |
|---|---|
| 楼栋集市作为唯一 P0 | 值得试点，但本楼商品不足时会切碎供给。默认展示全校并优先附近，保留本楼筛选；看分楼栋的有效供给与成交表现后再决定是否常驻。 |
| 本楼无结果自动扩到全校 | 必须标明“本楼暂无，以下为附近推荐”，与筛选结果分区展示；不能在用户选择“只看本楼”后悄悄改变范围。 |
| 卡片显示宿舍与步行分钟数 | 商品使用用户选择的交易点或交易楼栋，不默认公开居住楼栋。无路线数据时显示园区或大致距离，不伪造精确步行时间。 |
| 楼栋仅需一表两字段 | 还需学校/校区归属校验、交易点关联、数据维护、未知楼栋处理、隐私设置与查询索引；不能据字段数判断完整成本。 |
| 上架时同步匹配 | 保留“上架触发”，改为事务提交后异步处理。发布成功不依赖模型和通知服务；用可靠事件、幂等消费和失败重试保证送达。 |
| 热门型号排队 | 首版先做订阅通知。通知顺序不等于购买权；若做排队，需定义候选资格、预约期限、退出、并发锁定和过期释放，不宜只存可漂移的 position。 |
| 验货过程担保 | 改为“验货记录与争议辅助”。勾选不能证明物品无问题，也不能代替资金担保；增加未知、未检测、不适用状态。 |
| 与描述不符只能申诉 | 买家应能拒绝成交并记录原因。拒绝成交与卖家处罚分开，不能为防恶意举报强制买家继续交易。 |
| 履历真实且难伪造 | 平台订单仍可能互刷。展示双边确认的记录并注明来源，不宣称绝对真实；公开脱敏摘要，不开放他人完整订单。 |
| 替代信用分，同时爽约扣信用分 | 统一机制：用户侧优先展示可解释的履约事件和次数，内部限制由明确规则执行。新用户显示“记录不足”，不等同不可信。 |
| 10 分钟冷静期与爽约处罚 | 区分卖家接单前撤回、双方确认后取消、临近面交取消和实际爽约。取消不等于爽约；不得仅凭单方报告或 AI 判断处罚。 |
| 档期只有 TIME 与 weekdays | 模板可如此存储，但订单需保存具体日期、时区、起止时间、交易点和确认版本，改期后旧确认失效。 |
| 打包和单卖并存 | 必须共享库存：整包预约与任一单品预约互斥，事务内检查和锁定所有成员，取消后释放；不能只加 bundle_id。 |
| 毕业季卖给新生 | 供需季节可能错位，需验证校内交接时间。优先卖给在校生；没有存储与搬运能力时，不承诺跨暑假转交。 |
| 拍照发布与估价一起放到 P3 | 拆分。发布补全不一定依赖成交数据，可先做；估价要有足够同型号样本。线下实付价与挂牌价分开，未经确认不能称为成交价。 |
| 300 件、月收入 5000 元作为门槛 | 均缺少依据。改为试点假设，按品类覆盖、预约与履约表现、维护成本决定投入；总库存与收入不是每项功能的合理前置条件。 |

课程数据建议拆成课程目录、学期教学班、教材版本、教学班教材要求。课程名相同不代表教师、学期与版本要求相同；每条教材关系保留来源、核验状态、更新时间和纠错入口。

## 3. 建议新增的功能

### 3.1 需求翻译与匹配理由 · 优先试点

用户输入“想收一个晚上宿舍能用、不吵室友的小风扇”，系统辅助选择已有品类与需求标签，预算、校区等由用户确认。先检索候选，再判断商品描述与需求的相关性。

结果区分“满足已知条件”“仍有信息待确认”，例如“预算内；卖家未说明噪声”。理由来自可核对字段和模板，不能把“卖家没提噪声”写成“静音”。通知前再次检查商品仍在售、价格仍符合预算、订阅仍有效。

这可以承接原有需求雷达，不必新增独立 AI 聊天入口。

### 3.2 发布缺项提醒 · 优先试点

按品类检查重要信息：教材是否有版次、耳机是否含充电盒、台灯是否含电源。结构化必填用代码校验；文本中是否已表达某条信息，才使用语义判断。

只提醒用户补充缺失信息，不替用户声明“无维修”“电池健康”。首版不依赖照片识别，也不依赖成交数据。

### 3.3 教材版本核验助手 · 教材试点后开展

用户选择教学班，系统将商品 ISBN、版次和已核验的教材要求比较。精确标识比较由代码完成；课程别名、书名缩写等模糊关系由模型辅助选择候选。

展示“与已核验要求一致 / 明确不一致 / 待确认”。教材要求缺失时显示待确认，不用模型高置信度补出事实；跨版兼容由课程负责人或可靠资料确认。

### 3.4 在售新鲜度与到期复核 · 基础能力

长期未更新、卖家长期不响应的商品提醒确认仍在售；到期未确认降低曝光或暂停展示，允许恢复。避免需求雷达不断推送已线下卖出的物品。

这项主要用时间规则与交互完成，无需 AI。统计有效在售量时排除过期与暂停商品。

### 3.5 园区集中面交时段 · 有运营资源再试

提供经确认可用的公共交易点和集中时段，让买卖双方减少单独约时间的成本。先提供预约协调，不承诺代收、保管或到场认证；实际开放时间由运营维护。

## 4. TypeSafe 的合适边界

已核查官方重排、Choice、Score 与 Confidence 页面。文档索引和部分 Markdown 页面访问失败，改读可用的普通页面。本次只做方案设计，不锁定 SDK 版本、价格或延迟承诺。

| 判断 | 方法 | 业务使用方式 |
|---|---|---|
| 预算、在售状态、可见范围、学校、库存、档期交集 | 普通代码 | 硬条件过滤和权限控制，不能由模型覆盖 |
| 用户文本应归入哪个已有品类 | Choice | 选候选类别，保留“无匹配/需确认” |
| 某商品对一个使用场景的适合程度 | Score | 用明确的有序情境等级排序，证据不足单独处理 |
| 商品描述是否表达了指定缺陷或配件信息 | Noul | 分别判断窄问题，保留原文；缺少表述不代表不存在缺陷 |
| 模糊课程名应对应哪个课程候选 | Choice | 包含无匹配，不让模型编造候选之外的课程 |
| 精确教材版本是否一致 | 普通代码优先 | 缺少可靠字段则转待确认 |
| 确认交易、处罚、扣分、判断真假 | 规则与明确证据/人工流程 | 不交给模型独立裁决 |

TypeSafe 的重排示例采用“先快速检索候选、再逐对判断”的两阶段设计，可借鉴其结构，不能套用示例领域的准确率到校园商品。[官方重排示例](https://docs.typesafe.ai/cookbooks/rerank_typesafe)

Score 表示有序等级上的位置，confidence 表示答案分布的集中程度，不能解释成商品质量保证。对于场景适合程度，应使用具体等级描述，并与证据充分性分开。[Score 文档](https://docs.typesafe.ai/primitives/score)

Choice 用于候选项选择；候选集遗漏了正确课程或品类时，模型无法选出它，必须保留无匹配出口。[Choice 文档](https://docs.typesafe.ai/primitives/choice)

同一状态上的独立判断可放在一次请求中，问题不能依赖同批其他问题的答案。确有依赖时分阶段执行。Noul 接近 0.5 表示是与否难以区分，不表示“中等程度”；所有自动化阈值均需用本校样本评估。[Confidence 文档](https://docs.typesafe.ai/confidence)

### 需求雷达的最小流程

1. 发布事务同时记录商品版本与待处理事件，提交后立即返回发布成功。
2. 后台消费事件，以学校、可见范围、价格和在售状态过滤订阅与商品，再用关键词等召回候选。
3. 对有限候选执行语义判断，分开保存相关性、证据充分性、模型与问题版本。硬条件不能被综合分抵消。
4. 根据离线评估选出的策略决定通知、仅在应用内展示或请求补充；不把任意阈值写成行业标准。
5. 发送前复核商品和订阅最新版本、权限、通知许可与频率上限，按用户与商品去重，合并重复订阅。
6. 模型超时则退回规则结果；通知失败可重试。预约时仍由订单事务决定库存归属，AI 匹配不占库存。

模型调用放在服务端，密钥不进前端。仅发送判断必需的商品和需求内容，去除姓名、手机号、学号与不必要的居住信息。限制候选数与重试预算，记录调用成本和端到端耗时。

缓存键至少包含商品/订阅内容版本、模型版本与问题版本；商品改价、下架或权限变化后旧结果不得直接用于通知。用户文本是待分析内容，不可覆盖固定规则。

## 5. 建议实施顺序与验证方式

| 阶段 | 范围 | 验证重点 |
|---|---|---|
| A：跑通可信交易 | 附近优先、具体档期、取消/改期、在售复核、简版验货记录 | 有效供给、预约成功率、双方确认完成率、取消原因 |
| B：连接供需 | 规则版需求订阅、缺项提醒；语义匹配先影子运行 | 候选召回率、通知相关性、通知后有效咨询/预约、关闭通知率 |
| C：教材专项 | 小范围课程与版本关系、核验助手、学期订阅 | 版本误匹配率、课程覆盖、维护工时、教材成交 |
| D：扩展场景 | 并发库存完善后的打包出售、代发布、圈子 | 新增成交是否覆盖开发与运营成本，是否削弱公共供给 |

需求订阅不应机械等待 300 件商品，可先收集稀缺需求并人工撮合；语义模型只在规则匹配已暴露出实际漏匹配时引入。

验收数据建议从少量人工标注开始，覆盖中文简称、否定表达、无匹配、证据缺失、教材同名不同版、跨校同名楼栋、改价与下架、重复事件和服务超时。调参集与留出集分开，避免近重复商品泄漏。

同时观察召回阶段有没有漏掉正确商品，以及重排是否改善结果；分别统计规则基线与语义方案的效果。通知准确但召回很差，依然不能算成功。线上比较宜在相近时段与品类中进行，并记录样本量。

“纠纷率低于 2%”可以是目标，不能写成验货功能的已知效果。明确分母为完成交易还是全部预约，并给争议足够观察时间。平台双边确认完成也不等同独立核验的线下真实成交。

## 6. 实施前的数据模型补充

- 所有学校/校区/楼栋关联要校验一致性；圈子权限在查询、匹配和通知环节分别检查。
- `demand_matches` 增加订阅/商品版本、匹配来源、判断版本与状态；使用唯一约束实现幂等，并另行控制重复通知。
- 可靠事件保存处理状态、重试次数与下次重试时间；通知单独记录渠道、状态和去重键。
- 验货清单保存模板版本、下单时卖家描述快照、双方动作与时间；后续编辑商品不覆盖历史记录。
- 到达与出发属于用户自报状态，不作为实际到场证据；改期时重置并保留历史。
- 课程教材关系记录来源、适用学期/教学班、核验状态；UGC 合并与纠错留下历史。
- 代发布明确物主和发布者分别能编辑、接单、取消与处理争议的权限；“确认物主”不能只表现为一个布尔标签。

建议首个增量切片为：**规则版需求订阅 + 在售复核 + 发布缺项提醒**。它能同时减少无效供给和漏匹配，所需数据较少，也能为后续 TypeSafe 语义匹配积累真实评估样本。
