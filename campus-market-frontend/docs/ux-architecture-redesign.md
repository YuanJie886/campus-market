# 校园集市 · 用户体验架构重构方案

> 角色：用户体验架构师
> 范围：`campus-market-frontend`（React 18 + TS + Vite + MUI + Tailwind）
> 结论：**断点集中在「信息架构」与「交易闭环」两层，不是视觉问题。视觉已经足够好，不要再动它。**

---

## 0. 摘要

当前产品的视觉完成度很高（Apple Keynote 式 Hero、Scrollytelling 叙事、3D 倾斜卡片），但**把营销叙事放在了核心任务之前**，并且**把交易闭环拆断了**。

三条重构主线：

| # | 主线 | 一句话 |
|---|---|---|
| 1 | 首屏任务归位 | 首屏即商品广场，品牌叙事降级为可跳过的一屏 |
| 2 | 交易闭环补全 | 弹窗 → 确认页 → 成功页 → 订单详情页，每一步都有明确的下一步 |
| 3 | 订单与沟通合流 | 下单即建会话，订单卡片置顶聊天流；状态与"该谁动"显式绑定 |

诊断出 **6 个断点**，其中 3 个是阻断级（P0）。

## 1. 现状诊断

### 1.1 现状路由与导航

**路由表**（`src/App.tsx`）

```
/                          首页 = Hero 叙事 + Scrollytelling + 集市区块
/product/:id               商品详情
/login  /register
/publish                   发布（需登录）
/messages  /messages/:id   消息（需登录）
/profile                   我的（需登录，嵌套子路由）
  ├─ index                 资料
  ├─ listings              我的发布
  ├─ favorites             我的收藏
  └─ orders                我的订单
*                          404
```

**导航**（`Navbar.tsx` / `BottomNav.tsx`）

- 桌面端：Logo · 搜索 · 发布闲置 · 消息(红点) · 头像菜单（资料/发布/收藏/订单/退出）
- 移动端：首页 · 消息 · 发布(中央凸起) · 收藏 · 我的

**核心链路**（`ProductDetailPage.tsx` → `OrdersPage.tsx`）

```
商品详情 →「我想要」→ Dialog(面交点/时间/联系方式) → createOrder
        → navigate('/profile/orders')   ← 链路在此断掉
```

### 1.2 断点清单

| # | 环节 | 现象 | 根因 | 级别 |
|---|---|---|---|---|
| 1 | 进入首页 | 首屏是发布会叙事，真正的 `#marketplace` 在第 3 屏 | `HomePage` 把 Hero + Story 排在了 Market 之前 | **P0** |
| 2 | 找到商品 | 无独立搜索页、无分类页、无求购入口 | 搜索直接 `navigate('/?keyword=')`，与首页叙事混在一个路由；分类只能靠 `FilterBar` | **P0** |
| 3 | 发起交易 | 弹窗提交后直接跳订单列表，无确认页、无成功页、无金额确认 | `submitBooking()` 里 `navigate('/profile/orders')` 一步到位 | **P0** |
| 4 | 面交确认 | 无订单详情页；确认码、状态推进、评价全部挤在列表卡片上；买卖双方无会话 | 订单只有列表视图；下单不建会话 | P1 |
| 5 | 评价复购 | 评价入口弱；收藏后无降价/售出提醒 | 评价按钮只在 `COMPLETED` 卡片上；收藏是静态列表 | P1 |
| 6 | 登录中断 | 未登录点「发布/消息/收藏」→ 登录后一律回首页，丢失意图 | `Navbar`/`BottomNav`/`HomePage.goToPublish` 用裸 `navigate('/login')`，不带 `from`；只有 `ProductDetail.requireLogin` 传了 | P1 |

> 断点 6 的对比证据：`RequireAuth.tsx` 正确地传了 `state={{ from }}`，`LoginPage.tsx` 也正确地消费了 `redirectTo`。机制是完整的，只是**动作触发的跳转绕过了这套机制**。修复成本极低，收益立竿见影。

### 1.3 根因分析

1. **把「品牌表达」和「产品任务」放在了同一条滚动轴上。**
   Hero 和 Scrollytelling 是优秀的品牌素材，但它们是"一次性的"，而找货/出货是"每次都要做的"。两者共用首页 → 高频任务被低频内容挡住。

2. **把「表单」当成了「流程」。**
   `Dialog` 适合承载 3 个字段，不适合承载"确认交易条件"这件事。用户在这里需要看到：买什么、多少钱、卖给谁、去哪、什么时候、反悔成本——弹窗装不下，于是这些信息全部被省略了，闭环随之断裂。

3. **把「状态」当成了「标签」，而不是「引导」。**
   订单状态机（`PENDING_SELLER_CONFIRM → PENDING_MEETING → BUYER_CONFIRMED → COMPLETED`）在后端是完整的，但前端只把它渲染成一个 `Chip` 标签 + 一堆条件渲染的按钮。用户看到"待面交"，却不知道**该谁动、动什么**。

## 2. 设计原则

1. **任务优先，叙事后置。** 首屏回答"这里有什么"，而不是"我们是谁"。
2. **一个闭环，一条主链路。** 浏览 → 详情 → 确认 → 预约 → 面交 → 核验 → 评价，不允许任何一步把用户扔回列表。
3. **每一步都有明确的下一步。** 每个状态必须回答：我在哪、谁在等谁、我该点什么。
4. **沟通与交易不分离。** 订单即会话，会话即订单。
5. **信任前置到决策点。** 认证状态、成交数、好评率出现在"我想要"按钮旁边，而不是藏在个人主页。
6. **不动已经做对的视觉。** 设计系统（色彩、卡片、动效）保持不变，只重构结构与流程。

## 3. 目标信息架构

### 3.1 一级导航

| 平台 | 一级入口 | 变化 |
|---|---|---|
| 移动端 | **集市 · 求购 · 发布(+) · 消息 · 我的** | 「收藏」降级（从一级 Tab 移入「我的」），腾出位置给「求购」 |
| 桌面端 | **集市 · 求购 · 消息 · 发布闲置 · 我的** | 新增「求购」 |

> 为什么把「收藏」降级：收藏是低频的"存档"动作，不配占用一级 Tab。而「求购池」是产品定位里明确的核心差异化（`方案设计.md` 第二章），且能同时服务买家（发布需求）和卖家（匹配需求），必须有一级入口。

### 3.2 目标路由表

| 路由 | 页面 | 状态 |
|---|---|---|

| `/search` | 搜索结果页（独立承载关键词 + 筛选） | **新增** |
| `/category/:slug` | 分类页 | **新增** |
| `/product/:id` | 商品详情 | 增强 |
| `/checkout/:productId` | **确认预约页** | **新增** |

| `/wanted` | 求购池 | **新增** |
| `/wanted/new` | 发布求购 | **新增** |
| `/wanted/:id` | 求购详情 + 匹配结果 | **新增** |
| `/messages` `/messages/:id` | 会话（含订单卡片） | 增强 |
| `/notifications` | 通知中心（订单/匹配/降价/审核聚合） | **新增** |
| `/user/:id` | 卖家信用主页 | **新增** |

### 3.3 首屏重排

```
现状：  Hero(发布会)  →  Scrollytelling(3 幕)  →  Marketplace(筛选+商品)   ← 集市在第 3 屏
目标：  Marketplace(筛选+商品)  →  叙事/信任区块(可折叠)  →  页脚
                                  ↑ 品牌内容降级为「向下滚动才看到」
```

具体做法：把 Hero 与 Story 组件**原样保留**，但移到集市区块**之后**，并折叠为默认收起的「为什么选择校园集市」区块。视觉资产零浪费，任务路径从 3 屏缩短到 0 屏。

## 4. 核心流程重构

### 4.1 浏览 · 发现链路

```
现状：  首页(叙事→筛选)  ──搜索──▶  /?keyword=xxx  (回到首页叙事顶部)

目标：  首页(集市) ─┬─ 搜索框 ─▶ /search?q=xxx        独立结果页，筛选栏常驻
                    ├─ 分类 Tab ─▶ /category/:slug    独立分类页
                    └─ 商品卡 ─▶ /product/:id
```

**要点**
- `/search` 与 `/category/:slug` 独立成页，不再把筛选状态塞进首页 query。
- 首页 `FilterBar` 保留，但只做"轻筛选"，深度筛选引导到搜索页。
- 搜索结果页保留搜索历史与热门搜索（本地 `storage.ts` 已有基础）。

### 4.2 下单 · 履约链路（本次重构的重点）

```
现状（断裂）
商品详情 →「我想要」→ Dialog → createOrder → navigate('/profile/orders')
                                                  ↑ 无确认、无反馈、无指引

目标（闭环）
商品详情 →「我想要」→ 未登录？→ /login?from=/checkout/:id → 回跳
                  ↓ 已登录
          /checkout/:productId      确认预约页
             · 商品摘要 + 价格（唯一的"金额确认"机会）
             · 卖家信息 + 信用（认证/成交数/好评率）
             · 面交点选择（卡片式，非下拉）
             · 面交时间选择
             · 联系方式（默认回填 currentUser.contact）
             · 交易须知（平台不代收货款 / 六位确认码规则）
             · 主按钮「确认预约」 次按钮「先聊聊」
                  ↓ createOrder（带 idempotencyKey）
          /checkout/:productId/success   预约成功页
             · 明确告知「接下来等卖家确认」
             · 双出口：查看订单 / 和卖家聊聊
             · 同时静默建立买卖双方会话，并把订单卡片置顶
                  ↓
          /orders/:id              订单详情页
             · 时间线（下单 → 卖家接单 → 面交 → 核验 → 完成）
             · 面交信息卡（地点/时间/联系方式）
             · 六位确认码（仅买家可见，带防误传提示）
             · 按状态渲染的单一主操作按钮
             · 会话入口
```

**为什么确认页必须是页面而不是弹窗**
弹窗承载不了"确认交易条件"的认知负荷。用户在点下"确认预约"之前需要一次性看全：买什么、多少钱、卖给谁、去哪、什么时候、违约成本。这五类信息在同一屏内是"确认页"，拆进弹窗就是"漏填"。

**为什么下单要自动建会话**
现状「我想要」和「联系卖家」是两条互不相通的路径。下单后若想改时间地点，用户只能取消重来——因为没有会话通道。下单即建会话，把订单卡片注入聊天流，等于给每一笔订单配了一条"随时可协商"的旁路。

### 4.3 订单状态机与下一步引导

后端状态机不变，前端增加**显式引导层**：

| 状态 | 等待方 | 页面提示 | 主操作 | 次操作 |
|---|---|---|---|---|
| `PENDING_SELLER_CONFIRM` | 卖家 | 已通知卖家，通常 2 小时内回复 | 买家：取消预约 / 催一下<br>卖家：**接受预约** | 联系对方 |
| `PENDING_MEETING` | 双方 | 请按时到达面交点，当面验货 | 买家：**已验货付款，确认面交** | 改约（会话） |
| `BUYER_CONFIRMED` | 卖家 | 买家已付款，请核验确认码 | 卖家：**核验并完成交易** | — |
| `COMPLETED` | 双方 | 交易完成 | **评价对方** | 再逛逛 |
| `CANCELLED` / `EXPIRED` | — | 商品已回到在售 | 重新预约 | — |
| `DISPUTED` | 平台 | 已受理，24 小时内介入 | 补充举证 | — |

**关键改动**
- 新增 `/orders/:id`，把确认码、状态推进、评价**从列表卡片迁移到详情页**。列表只保留：商品缩略、金额、状态 Chip、**一个主操作按钮**（引导进详情）。
- 确认码规则在详情页显式说明："面交验货、付款完成后，再告知卖家。"
- 每个状态卡片顶部固定一行"当前等待：XXX"。

### 4.4 消息与订单合流

```
现状：  消息 = 纯文本会话列表
目标：  消息 = 会话 + 系统通知，且会话流内可插入「订单卡片」消息类型
```

- `MessagesPage` 会话流新增 `type: 'order'` 的消息渲染（商品图 + 状态 + 跳转 `/orders/:id`）。
- 新增 `/notifications`：订单状态变更、求购匹配、收藏商品降价、审核结果，统一聚合，替代现在只能靠轮询红点感知的体验。
- 现状 `MarketContext` 的 15 秒全量轮询保留为降级方案，实时通道（SSE / WebSocket）列入 P2。

## 6. 前端架构改造

### 6.1 状态管理：从「全量内存」到「查询层」

**现状问题**（`src/context/MarketContext.tsx`）

```ts
// 循环拉取全部商品进内存，前端过滤
for (let page = 1; ; page++) {
  const result = await api.listProducts({ sort: "latest", page, pageSize: 100 });
  products.push(...result.items);
  if (products.length >= result.total || !result.items.length) break;
}
```

这套设计在商品量上到几千件时会直接拖垮首屏，且 `setInterval` 15 秒全量刷新一次。

**目标**

| 现状 | 目标 |
|---|---|
| 全量商品常驻内存 | 列表页分页 / 无限滚动，服务端筛选 |
| `MarketContext` 单一大 Context | 拆分为 `AuthContext` / `MarketQueryContext`（列表）/ `OrderContext` / `ChatContext` |
| 15s 全量轮询 | 仅轮询"未读数"与"进行中订单"两个轻量端点；P2 换 SSE |
| 前端 `filtered` 计算 | 筛选条件序列化为 query，交给 `/v1/products` |
| 无缓存 | 详情页 / 会话列表做短 TTL 缓存 |

**落地建议**：不引入 Redux。用「轻量 Context + 自定义 hook（`useProductsQuery` / `useOrderDetail`）」即可，保持现有技术栈。

### 6.2 认证断点统一修复

新增统一的鉴权跳转入口，替换所有裸 `navigate('/login')`：

```ts
// src/hooks/useAuthGate.ts
export function useAuthGate() {
  const { isAuthenticated } = useAuth();
  const navigate = useNavigate();
  const location = useLocation();
  return useCallback((action: () => void) => {
    if (isAuthenticated) return action();
    navigate('/login', {
      state: { from: `${location.pathname}${location.search}` },
    });
  }, [isAuthenticated, navigate, location]);
}
```

替换点（当前全部缺失 `from`）：
- `src/components/Navbar.tsx` → `handlePublish` / `handleMessages`
- `src/components/BottomNav.tsx` → `handleClick`
- `src/pages/HomePage.tsx` → `goToPublish`

### 6.3 三态规范（加载 / 空 / 错误）

现状是散落的 `<p>正在加载商品…</p>` 与零星的 `EmptyState`。统一为：

| 态 | 规范 |
|---|---|
| Loading | 骨架屏，形状对齐真实内容（商品卡 = 图 + 两行文案） |
| Empty | `EmptyState` 组件 + 明确的下一步动作（"去发布" / "清空筛选"） |
| Error | 保留 `Layout` 的错误条，但错误信息要可操作（"网络异常，重试"） |

### 6.4 路由守卫

`RequireAuth` 已正确实现，保持不变；新增 `/checkout`、`/orders`、`/wanted/new` 时复用。

## 9. 功能创新机会

> **完整方案已独立成文：[`feature-innovation.md`](./feature-innovation.md)。**
> 本章仅保留摘要与结论，避免两份内容日后各自漂移。功能创新的唯一权威来源是该独立文档。

本方案前 8 章解决"断点"，第 9 章解决"差异化"。两者不冲突：**先修断点，再建壁垒。**

### 9.1 判断标准

一个功能值不值得做，只问一句：**闲鱼能不能抄走？**

能抄的只是功能，抄不走的才是壁垒。校园平台真正独有的只有三样：**课程表、宿舍楼、班级群**。所有创新都应围绕这三层密度展开。

### 9.2 三重校园密度

| 密度层 | 定义 | 对应创新 |
|---|---|---|
| 课程密度 | 时间轴上的同一门课 | 课程教材图谱、学期轮回匹配 |
| 空间密度 | 同一栋宿舍楼 | 楼栋集市、面交档期握手、出发·已到同步 |
| 关系密度 | 班级 · 社团 · 宿舍群 | 圈子集市、班级代发布 |

闲鱼拥有"全国密度"，但这三层校园密度它一层都拿不到。

### 9.3 优先级摘要

独立文档共收录 13 项创新。前三项：

| 排序 | 创新点 | 优先级 | 理由 |
|---|---|---|---|
| 1 | **楼栋集市** | P0 | 成本最低（1 表 + 2 字段 + 排序开关），直接打成交率：面交成本从"走 10 分钟"降到"上下楼" |
| 2 | **需求雷达 + 排队** | P1 | 直接打冷启动。把求购从"发帖等人看"改为"订阅 + 上架即命中" |
| 3 | **结构化验货清单** | P1 | 平台不代收货款 → 无法用资金担保 → 只能**担保验货过程** |

### 9.4 明确不做

AI 识真、自制担保支付、复杂社区动态 / 直播、实时位置共享、积分提现 / 虚拟货币。

共同特征：**看起来创新，但不解决早期的密度问题**（与 `方案设计.md` 第十三章一致）。

## 10. 盈利模型

> 本章**细化** `方案设计.md` 第九章「盈利路径」，不是替换。
> 区别：`方案设计.md` 按"阶段"排列收入项；本章按"付费方 + 解锁条件"排列，并补上单校区测算与合规红线。

### 10.1 先排除一个错误答案：交易佣金

**测算**：校园二手 AOV 约 ¥30–80（教材、小电器为主），单用户年成交 3–8 次。抽 5% → 每单 ¥1.5–4。

**结论：交易佣金结构性不成立，永远不做。** 三条理由：

1. 单笔金额太小，覆盖不了支付通道 + 纠纷处理成本；
2. 必然驱使双方绕开平台走微信——损失的是交易数据与留存；
3. 与第一阶段目标（提高商品量与成交密度）直接冲突。

### 10.2 三个付费方

| 付费方 | 为什么付钱 | 收入形态 |
|---|---|---|
| 校园商户 | 为「获客」付钱 | 认证商家月费 / 服务线索费 / 优惠券核销服务费 |
| 学生用户 | 为「省时间·降风险」付钱 | 官方验机 / 校园跑腿交付 / 毕业季清仓推广包 |
| 平台自身 | 从「回收差价」赚钱 | 整间宿舍打包回收 / 专业回收转售差价 |

### 10.3 单校区稳态收入测算

**前提**：5000 学生 / 30% 渗透 / 单校区运营成熟。

| 收入项 | 付费方 | 计价 | 月量 | 月收入 |
|---|---|---|---|---|
| 认证商家月费 | 商户 | ¥299/月 | 8 家 | ¥2,392 |
| 服务线索费 | 商户 | ¥15/条 | 40 条 | ¥600 |
| 券核销服务费 | 商户 | 核销额 8% | ¥6,000 | ¥480 |
| 官方验机 | 用户 | ¥30/台 | 50 台 | ¥1,500 |
| 跑腿抽成 | 用户 | ¥3/单 | 400 单 | ¥1,200 |
| 清仓推广包 | 用户 | ¥19.9/份 | 毕业季 60 份 | ¥1,194 |
| 打包回收差价 | 平台 | ¥80/间 | 毕业季 30 间 | ¥2,400 |
| 交易佣金 | — | — | — | **¥0（刻意不做）** |

- 平月 ≈ **¥6,200**
- 毕业季月 ≈ **¥9,800**
- 年化 ≈ **¥8 万 / 校区**

> 这是**稳态测算，不是预测**。达成前提见 10.4。

### 10.4 变现解锁阶梯

| 阶段 | 解锁条件 | 可启动的收入项 |
|---|---|---|
| 1 用户规模起来 | 单校活跃用户 ≥ 1000 | 认证商家月费、服务线索费、券核销服务费 |
| 2 交易密度起来 | 在售 ≥ 300 件 · 周成交 ≥ 30 单 | 官方验机、校园跑腿、清仓推广包 |
| 3 运营成熟 | 单校稳态月收入 ≥ ¥5,000 | 打包回收转售、专业回收差价、多校复制 |

**关键洞察：商户侧的收费门槛远低于用户侧。**

商户购买的是"这里有多少学生"（用户规模），不是"这里成交多少单"（交易密度）。因此活跃用户过千即可启动商户侧变现，而增值服务必须等交易密度成立。

反过来说：**在商品密度不足时向用户收费，会直接杀死流动性。** 用户侧收费的前提是"平台已经帮他成交过"，而不是"平台需要钱"。

### 10.5 一个决定产品设计的结论：规模来自校数，不来自单校深度

单校区天花板约 ¥8 万/年。这个数字不高，它推导出三条硬约束：

1. **商业模型必须可复制**——每多一个校区，边际成本必须趋近于零；
2. **不能做依赖大量人工审核的功能**——人工审核无法跨校区复制；
3. **必须有校园运营官体系**——用学生代理承担 BD 与地推，而不是总部雇人。

这三条反过来约束产品设计：凡是需要总部人工介入的功能（人工认证审核、人工纠纷仲裁、人工代发布），要么自动化，要么下沉到校区。

### 10.6 合规红线

| 红线 | 原因 |
|---|---|
| 不碰资金 | 一旦代收货款，涉及商户资质、退款、分账、财税、平台责任 |
| 商户与学生闲置必须明确区分 | 否则平台被商业商品淹没，用户流失 |
| 不做学生信用数据对外输出 | 个人信息保护法风险极高 |
| 不承诺绝对安全 | 平台责任边界必须清晰 |

### 10.7 收入项与产品功能的对应关系

| 收入项 | 依赖的产品功能 | 当前状态 |
|---|---|---|
| 认证商家月费 | 商户主页 + 服务目录 | 未开发 |
| 服务线索费 | 需求派单 | 未开发（可复用需求雷达） |
| 券核销服务费 | 优惠券系统 | 未开发 |
| 官方验机 | 验机预约 + 验机报告 | 未开发（与结构化验货清单同源） |
| 校园跑腿 | 跑腿下单 | 未开发 |
| 清仓推广包 | 毕业季打包 + 支付 | 未开发 |
| 打包回收转售 | 回收估价 + 批量受理 | 未开发 |

> **上表 7 项全部未开发。** 这意味着当前阶段**不应考虑盈利**，而应把资源全部投入 P0 断点修复与商品密度建设。盈利模型是"条件满足时照着做"的说明书，不是"现在就该做的事"。
