## 1. 项目信息与现状

- **Project Name**：`campus_market`
- **产品名称**：校园集市
- **语言**：中文
- **当前技术**：Vite + React 18 + TypeScript + MUI + Tailwind CSS + React Router
- **目标技术演进**：保留现有 Web 端；新增 NestJS API、PostgreSQL、Redis、对象存储；后续以 Taro + React + TypeScript 建设微信小程序，以 React + Ant Design 建设运营后台。
- **当前可见能力**：首页搜索/筛选/排序、商品详情、发布、登录/注册、收藏、留言及回复、站内会话消息、订单、个人中心（资料/我的发布/收藏/订单）。当前核心业务数据主要通过 `localStorage` 持久化，需迁移至服务端。

## 2. 产品定义

### 2.1 目标

1. **提高同校交易效率**：让学生能快速发现、咨询并预约同校闲置，北极星指标为每周成功完成的真实交易数。
2. **建立校园可信交易环境**：通过校园身份认证、公开交易点、订单确认码、评价与举报降低交易风险。
3. **形成供需差异化闭环**：以求购池与商品智能匹配连接买卖双方，优先在单校/单校区验证商品密度与成交效率。

### 2.2 一句话定位

> 只和同校同学交易、支持安全面交和求购匹配的校园闲置集市。

### 2.3 目标用户

- 低价购买教材、数码、生活用品的在校学生；
- 毕业、换宿舍、清理闲置的学生；
- 新生集中采购物品的学生；
- 社团、实验室、宿舍等批量转让闲置物资的用户。

## 3. 范围与版本边界

### 3.1 本阶段范围（单校灰度 MVP）

- Web 端真实后端化：用户、商品、收藏、订单、消息等核心数据走 API；
- 微信小程序端核心交易链路：登录/认证、浏览搜索、发布、收藏、咨询、预约面交、订单完成；
- 基础运营后台：认证审核、商品审核、举报处理、用户封禁、交易点配置、审计日志；
- 站内通知与可选微信订阅消息（仅在用户主动授权后发送）；
- 单校/校区内线下面交，不接二手商品平台代收款。

### 3.2 明确不做（本阶段）

自制担保支付、直播卖货、复杂社区动态、积分提现、全国跨校交易、实时位置共享、复杂 AI 聊天机器人、自动鉴定真伪、大规模微服务拆分。

## 4. 用户故事

1. **作为买家**，我想按关键词、分类、校区、价格和成色搜索商品，以便快速找到适合自己的闲置。
2. **作为卖家**，我想发布带图片、成色、价格、校区和议价设置的商品，以便在校内找到买家。
3. **作为已认证学生**，我想在商品详情中联系卖家并选择公共面交点/时间，以便安全完成交易。
4. **作为买家**，我想发布求购信息并接收相似商品匹配，以便不用反复搜索也能找到目标物品。
5. **作为交易双方**，我想看到订单状态、六位确认码并互相评价，以便明确交易责任并积累信用。
6. **作为运营人员**，我想审核认证、处理举报和下架违规内容，以便维持校园市场秩序。

## 5. 需求池

### P0（必须上线）

#### 账户与校园身份

- 微信授权登录；Web 端保留账号登录兼容方案；
- 手机号绑定、学校/校区选择、昵称/头像/联系方式维护；
- 校园认证状态展示，首版支持校园邮箱验证码与人工审核并行；
- 注销账号、退出登录；服务端不得信任前端传入的用户 ID；密码不得明文存储。

#### 商品与搜索

- 发布/编辑/下架/重新上架；图片上传、压缩与内容检测；
- 标题、描述、分类、成色、价格、校区、联系方式、议价开关；
- 关键词搜索、分类/校区/价格/成色筛选及最新/价格/热度排序；
- 浏览、收藏、分享、相似商品推荐；过期商品自动下架；商品举报。

#### 交易与消息

- 交易采用“线上预约、线下面交、双方自行付款”；
- 订单状态至少覆盖：待卖家确认 → 待面交 → 买家确认完成 → 卖家确认完成 → 已完成，并支持已取消/已超时/申诉中；
- 订单记录面交时间、固定公共交易点、联系方式、六位交易确认码、状态流水；超时自动释放商品，避免重复创建；
- 商品咨询、会话消息、订单通知、未读数量；关键消息可在用户主动授权后发送微信订阅消息；
- 完成交易后双方可评价。

#### 运营与安全

- 后台用户管理、认证审核、商品审核、举报/申诉处理、敏感词管理、用户封禁/解封；
- 所有资源按归属鉴权，记录操作审计日志；文本/图片采用机器检测 + 敏感词 + 举报 + 人工复核；
- 隐私政策、用户协议、交易规则、发布规范、举报申诉规则、个人信息清单和删除机制。

#### 基础设施

- NestJS + PostgreSQL + Redis + 对象存储；核心业务不再依赖 `localStorage`；
- 提供 API 规范与 Swagger/OpenAPI 文档；开发/测试/生产环境隔离；数据备份与恢复演练。

### P1（应上线/验证差异化）

- 求购池：商品名称、预算、期望成色、校区、期望时间、可接受相似商品；
- 基于标题/分类/价格/校区/关键词的匹配分数；新商品匹配既有求购、求购匹配新商品，并产生站内/订阅提醒；
- 降价提醒、搜索历史、热门搜索、拼写容错；
- 校园信用摘要：完成交易数、好评率、注册时长、认证状态、取消/核实举报次数、平均回复时间；不展示完整学号/手机号/身份证；
- 小程序首页、分类、详情、发布、收藏、个人中心、我的发布、求购信息页面；
- 后台首页推荐位、Banner/活动、分类、校区及固定交易点配置；数据看板（供给、咨询、预约、成交、纠纷）。

### P2（Nice to have）

- 毕业季清仓合集：多件批量发布、单买/打包价、宿舍整套转让、批量购买；
- 清仓倒计时、分享海报/卡片、邀请机制；
- 校园活动（开学装备节、教材交换周、毕业季清仓等）；
- 积分兑换置顶/急售标签/商户优惠券（首版禁止提现）；
- 审核商户入驻、推广位和毕业清仓推广包；后续再评估验机、跑腿、专业回收等增值服务。

## 6. 页面与交互要求

### 6.1 Web 用户端（延续现有页面）

- **首页**：Hero、搜索框、筛选条、商品网格；空结果提供重置筛选/发布入口；搜索条件可由 URL 恢复。
- **商品详情**：图片画廊、价格/成色/校区/浏览量、卖家卡、收藏、联系卖家、留言/回复、相关推荐；未登录时联系方式脱敏，敏感操作引导登录。
- **发布/编辑**：分步或分区表单；图片上传预览/删除/压缩；必填校验、价格区间校验、议价开关；提交后进入审核或直接上架（由运营策略配置）。
- **消息**：会话列表、按商品关联会话、消息时间线、发送、未读标记；订单/匹配/降价通知可筛选。
- **个人中心**：资料与认证状态、我的发布（编辑/下架/重上架/标记售出）、收藏、买卖订单、评价与注销。

### 6.2 小程序端

- 使用 Taro + TDesign/NutUI 重做组件，不直接复用 MUI DOM 页面；优先保证登录—发布—搜索—收藏—咨询—预约面交链路在主流手机尺寸可用。
- 分享链接必须能直达对应商品或清仓合集；订阅消息前明确告知用途并获得用户主动授权。

### 6.3 运营后台

- 左侧导航：用户/认证、商品、举报申诉、订单、内容规则、交易点、活动推荐、数据看板、审计日志；
- 审核列表支持状态筛选、详情查看、证据留存、处理备注、批量下架/封禁；所有高风险动作需二次确认并留痕。

### 6.4 交易交互规则

- 下单前展示面交安全提示和“平台不代收商品款”说明；
- 买家发起预约，卖家确认后进入待面交；双方均确认完成才结算为已完成；
- 取消/超时需说明原因，商品按规则释放；申诉时冻结相关订单操作并保留聊天、订单流水和举证。

## 7. 验收标准

### 功能验收（P0）

1. 两个不同账号在同一校区可完成登录/认证、发布商品、搜索、收藏、咨询、预约面交、双方确认完成和评价；
2. 商品、用户、收藏、订单跨设备可见，刷新或重新登录不丢失；浏览器 `localStorage` 仅用于令牌、搜索历史、UI 偏好和草稿；
3. 普通用户无法读取或修改他人的商品、订单、认证资料；同一商品不能被重复下单；取消/超时可按规则释放；
4. 管理员可审核认证、下架商品、处理举报、封禁用户，且每次处理含操作者、时间和原因；
5. 联系方式、学号等敏感信息默认脱敏；注销后按策略删除或匿名化个人信息；
6. API 提供可访问的 Swagger/OpenAPI 文档，数据库具备备份与恢复验证记录。

### 质量与运营验收

- 关键交易链路在主流移动端尺寸无阻断；图片加载失败有占位和重试；表单错误可理解且可修复；
- 试运营以单校为单位，目标值（非行业标准）：有效在售商品 ≥300 件；周新增 ≥100 件；发布后 7 天内产生咨询比例 >30%；预约到成交 >50%；纠纷率 <2%；30 日交易用户留存 >20%。
- 核心漏斗需埋点：有效商品新增、详情→咨询、咨询→预约、预约→完成、平均成交时长、取消/举报/纠纷、分享带新。
