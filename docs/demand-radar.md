# 需求雷达：订阅、同步匹配与收件箱

本文档说明模块 2「需求雷达核心版」的设计。实现与测试以此为准。

---

## 1. 产品目标

买家在首页搜不到想要的东西时，可以把这次搜索存成一条**需求订阅**。
之后任何一件新商品发布，只要符合订阅条件，买家就会在「需求匹配」里看到它。

## 2. 为什么不是普通求购帖

| | 求购帖 | 需求雷达 |
|---|---|---|
| 谁去找谁 | 卖家得主动翻帖才会知道有人想要 | 商品发布时由服务端主动比对 |
| 时效 | 帖子沉底即失效 | 订阅一直有效，直到用户停用 |
| 隐私 | 求购内容公开，谁都能看到谁想要什么 | 订阅只有本人可见，卖家看不到任何订阅者 |
| 议价 | 卖家看到求购人数后可以抬价 | 卖家拿不到命中人数 |

## 3. 数据模型（V4）

迁移文件：`campus-market-backend/src/main/resources/db/migration/V4__demand_radar.sql`

### 3.1 `demand_subscriptions`

| 列 | 说明 |
|---|---|
| `id` | uuid |
| `user_id` | 订阅人。**只来自认证身份** |
| `school_id` | 由用户校区推导，客户端无法指定 |
| `keyword` / `normalized_keyword` | 原文用于展示；规范化值用于匹配，1～40 字 |
| `category` | 可空，不限分类 |
| `min_price` / `max_price` | 可空，非负，`min ≤ max` |
| `geo_scope` | `BUILDING` / `ZONE` / `CAMPUS` / `SCHOOL` |
| `campus_id` / `building_id` | 范围锚点。ZONE 的园区由楼栋推导 |
| `fingerprint` | 服务端对规范化条件求的 SHA-256，用于幂等 |
| `active` | 删除即软停用 |
| `created_at` / `updated_at` | |

数据库层面的约束（任何绕过服务层的写入也无法违反）：

- 至少要有关键词或分类之一；
- 每种范围的锚点必须齐全且不多余，由一条 CHECK 约束保证；
- 复合外键 `(campus_id, school_id) → campuses(id, school_id)`：校区不可能来自另一所学校；
- 复合外键 `(building_id, campus_id) → buildings(id, campus_id)`：楼栋不可能来自另一个校区；
- 部分唯一索引 `(user_id, fingerprint) WHERE active`：同一用户同样条件只能有一条启用中的订阅。

### 3.2 `demand_matches`

匹配记录**本身就是通知**，不另建通知表。

| 列 | 说明 |
|---|---|
| `subscription_id` / `product_id` | `(subscription_id, product_id)` 唯一 |
| `score` | 0～100 |
| `reason_codes` | 与评分一一对应的理由码，只允许已知常量 |
| `read_at` / `dismissed_at` / `invalidated_at` | 均不早于 `created_at` |

表中**没有任何队列位置字段**（见第 10 节）。

### 3.3 索引

| 索引 | 用途 |
|---|---|
| `demand_subscriptions_match_category (school_id, category) WHERE active` | 发布时的候选查询 |
| `demand_subscriptions_match_building / _campus WHERE active` | 地理锚点 |
| `demand_subscriptions_user_created` | 我的订阅列表 |
| `demand_matches_product` | 商品编辑时找回全部匹配 |
| `demand_matches_subscription_created` | 收件箱 |
| `demand_matches_unread WHERE 未读未忽略未失效` | 未读数 |

## 4. API

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/v1/demand-subscriptions` | 创建，幂等 |
| GET | `/v1/demand-subscriptions` | 我的订阅（含已停用） |
| PATCH | `/v1/demand-subscriptions/{id}` | 修改条件或启用状态 |
| DELETE | `/v1/demand-subscriptions/{id}` | 软停用 |
| GET | `/v1/demand-matches?page=&pageSize=` | 收件箱 |
| GET | `/v1/demand-matches/unread-count` | 未读数 |
| POST | `/v1/demand-matches/{id}/read` | 标记已读，幂等 |
| POST | `/v1/demand-matches/{id}/dismiss` | 忽略，幂等 |

全部需要登录。可写字段只有 `keyword`、`category`、`minPrice`、`maxPrice`、`geoScope`、`campusId`、`buildingId`（PATCH 另加 `active`）。
其余字段（包括 `userId`、`schoolId`、`fingerprint`、`zone`）一律返回 400，**无副作用、不回显**。

### 4.1 创建的固定语义

| 情况 | `outcome` | 行为 |
|---|---|---|
| 已有同条件的启用订阅 | `EXISTING` | 返回原订阅，不新建 |
| 只有同条件的已停用订阅 | `REACTIVATED` | 重新激活最近那一条，历史匹配仍挂在它下面 |
| 否则 | `CREATED` | 新建 |

「同条件」按规范化后的条件判断：大小写、全角空格、连续空白都不影响；价格 10 与 10.00 视为相同；
ZONE 范围以「校区/园区」为锚点，同园区换一栋楼当锚点仍是同一订阅。

### 4.2 范围规则

| 范围 | 规则 |
|---|---|
| SCHOOL | 不得带校区或楼栋 |
| CAMPUS | 缺省为本人校区；校区必须属于本人学校 |
| BUILDING / ZONE | 缺省使用本人宿舍楼；没有宿舍楼也没选楼返回 **409**；楼栋不存在 404、停用 400、跨校 400 |

### 4.3 数量上限

每人最多 **50** 条启用订阅，超过返回 409。并发安全：创建时先 `SELECT ... FOR UPDATE` 锁住用户行，
「计数 → 判断 → 插入」在同一事务内串行化；部分唯一索引是最后一道防线。**不使用单机内存计数器。**
突变测试已验证：去掉这把锁后，20 个并发请求会让用户停在 56 条。

## 5. 同步匹配事务

商品**发布、编辑、上下架**都会在同一事务里调用 `DemandMatchService.evaluate(productId)`，
它的事务传播是 `MANDATORY`：脱离商品事务调用会直接报错。

- 发布接口返回成功时，匹配已经提交，不依赖任何扫描任务、消息队列或前端重新搜索；
- 匹配失败则商品一并回滚，接口返回 500，不存在「发布成功但没有匹配」的中间态；
- 事务内不发送任何外部消息，不调用任何推送服务。

一次评估的语句数是固定的，与命中订阅数无关：

1. 读商品；
2. 查学校；
3. 查候选（一条 SQL，全部硬性条件都在里面）；
4. 批量 UPSERT；
5. 失效其余。

实测命中 386 条订阅时为 5 条语句。

## 6. 匹配规则与评分

### 6.1 硬性条件（全部满足才是候选）

1. 订阅启用；商品在售；同一学校；不是卖家本人的订阅；
2. 价格落在区间内（含边界）；
3. 订阅有分类时必须一致；
4. 订阅有关键词时，**规范化标题或描述**必须包含**规范化关键词**；
5. 地理范围：BUILDING 同楼，ZONE 同校区且同园区，CAMPUS 同校区，SCHOOL 同校。

关键词比较用 `strpos` 做字面子串包含，**不用 LIKE**：`%` 与 `_` 永远是普通字符。
规范化只在 Java 的 `DemandText` 里做一次，SQL 只比较结果，前端 Mock 的 `normalizeDemandText` 与之逐条一致。
不引入 Elasticsearch，也不做语义匹配。

### 6.2 评分

| 理由码 | 分值 | 条件 |
|---|---|---|
| `KEYWORD_TITLE_EXACT` | 50 | 规范化标题与关键词完全相同 |
| `KEYWORD_TITLE` | 40 | 标题包含关键词 |
| `KEYWORD_DESCRIPTION` | 20 | 仅描述包含 |
| `CATEGORY` | 20 | 订阅指定了分类且命中 |
| `SAME_BUILDING` | 20 | 商品在锚点楼栋 |
| `SAME_ZONE` | 12 | 商品在锚点园区（非同楼） |
| `SAME_CAMPUS` | 6 | 校区范围命中 |
| `PRICE_CLOSE` | 10 | 有上下限且价格在区间中间一半 |

三个关键词理由互斥，三个地理理由互斥，满分为 50 + 20 + 20 + 10 = 100。
后端唯一实现是 `DemandScorer`，前端唯一实现是 `utils/demand.ts`，两边有对照测试。
界面只展示档位（≥60 为「高匹配」，其余为「一般匹配」），不同时展示原始分数，避免两套口径。

### 6.3 编辑与状态变化

- 新满足条件 → 新增匹配；
- 不再满足 → 标记 `invalidated_at`，**不删除**；
- 重新满足 → 同一条记录恢复有效，不会产生第二条；
- 已读、已忽略的状态在重新评估时保持不变；
- 被预约或售出时，商品状态在读取时即时反映为「不可购买」，不依赖订单流程回调。

### 6.4 不回溯

订阅只匹配**之后**发布或编辑的商品，创建时不回扫已有商品。
这是有意的：它与「有货第一时间通知你」的承诺一致，也避免一次订阅引发全表扫描。

## 7. 隐私边界

| 规则 | 保证方式 |
|---|---|
| 卖家看不到订阅者 | 不存在任何「按商品列订阅者」的读路径 |
| 卖家拿不到命中人数 | 发布与编辑响应都不含匹配信息（有测试覆盖） |
| 买家只看到自己的匹配 | 查询以 `s.user_id = 当前用户` 为前提；他人的匹配 id 读写一律 404 |
| 收件箱不泄露卖家联系方式 | 商品按非本人视角投影 |
| 身份不可伪造 | 用户、学校、指纹全部由服务端决定 |

## 8. 未读与刷新机制

未读数只统计以下条件同时成立的匹配：未读、未忽略、未失效、商品在售、订阅启用。

本阶段**不引入 WebSocket**，刷新时机只有：

- 登录后首次加载；
- 页面重新获得焦点，或从后台切回前台；
- 在收件箱里操作之后主动刷新；
- 前台时每 60 秒轮询一次。

约束：

- 未登录不轮询；页面在后台时不轮询；
- 登出立即停止并清零，卸载时取消；
- 失败后指数退避，最长 5 分钟；
- 429 严格按 `Retry-After` 等待。

全站只有一个轮询器（`DemandUnreadProvider`），导航栏角标与收件箱共用。

**不申请浏览器系统通知权限，不发短信、微信或邮件。**

## 9. 搜索空态入口

首页搜索或筛选结果为空时，商品区里直接出现：「没有找到？订阅一下，有货第一时间通知你。」

- **预填**：关键词、分类、价格与地理范围都取自当前的筛选**状态**，而不是展示文案。
  开启「只看本楼」时为 `BUILDING`，选了校区时为 `CAMPUS`，否则为 `SCHOOL`。
- **未登录**：条件草稿存入 `sessionStorage`（只含条件，不含任何认证信息），登录后回到同一搜索页并自动打开确认框。
- **重复条件**：提示「你已经订阅过相同条件」，不重复创建。
- **创建成功**：可以撤销（软停用），也可以跳转「管理订阅」。

## 10. 为什么本阶段没有排队

「热门型号排队」需要回答一个问题：排在第 1 位的人拿到了什么？如果答案是「和第 10 位同时收到通知」，
那么队列位置就是虚构的，展示它会误导用户。因此本阶段**不展示任何队列位置**，表结构里也没有这类字段。

将来要做真正的排队，至少需要：

1. **独占通知窗口**：只通知队首，在窗口期内其他人看不到或不能下单；
2. **响应期限**：队首在限定时间内不响应即视为放弃；
3. **自动递补**：放弃或超时后顺延给下一位，且能被审计；
4. **取消与重新排队**：规则明确，不能靠反复取消插队；
5. **防刷**：限制小号批量占位；
6. **公平性**：排序依据公开、可解释，卖家不能指定插队。

这些规则都没有设计之前，任何「你排在第 N 位」都不应该出现。

## 11. 已知局限

- 关键词是字面子串匹配：「耳机」能匹配「蓝牙耳机」，但「AirPods」不会匹配「苹果耳机」。
- 前端价格计算使用浮点数，与后端 BigDecimal 在极端小数边界上理论上可能相差一个分值档位。
  价格最多两位小数，实际测试中没有出现差异。
- 订阅不回溯已有商品（见 6.4）。
