# 微信小程序迁移方案

评估日期：2026-10-09。目标平台已确认为微信小程序；本文为目标迁移路线。第一版工程已位于 `campus-market-miniapp/`，使用现有账号登录，支持演示模式和现有后端的 REST 适配。微信登录和服务端图片上传尚未接入，具体体验方式与当前范围见 [小程序说明](../campus-market-miniapp/README.md)。

下文描述完整迁移的目标与验收要求；已交付第一版的实际能力以小程序说明为准。

## 推荐路线

新增 `campus-market-miniapp/`，采用 Taro 4.x + React 18 + TypeScript。沿用现有 Spring Boot、PostgreSQL 和 Web 管理后台。学生端页面按小程序交互重新实现，逐步提取可以共享的类型、校验和格式化函数。

选择 Taro 的依据是现有学生端已经使用 React 18 与 TypeScript，可以继续使用熟悉的组件、状态与 Hooks 写法。Taro 的页面、组件和路由遵循小程序规范，现有 Web 页面仍需要适配，尤其是 MUI 和依赖浏览器的组件。

官方参考：[React 使用概述](https://docs.taro.zone/docs/react-overall)、[React 18 支持](https://docs.taro.zone/docs/react-18)、[小程序组件规范](https://docs.taro.zone/docs/components-desc)。

## 现有工程的复用边界

| 部分 | 处理方式 | 本项目依据 |
| --- | --- | --- |
| 商品、收藏、学校及圈子可见性、联系申请 | 复用后端业务和接口，按需补适配接口 | `CampusMarketController`、`ContactRequestController`、`MarketService` |
| PostgreSQL 数据与历史记录 | 继续使用；新增能力通过新 Flyway 迁移加入 | 当前业务已有持久化和迁移管理 |
| React Admin 管理后台 | 继续作为 Web 后台 | `campus-market-admin/` 已独立于学生端 |
| TypeScript 类型、纯函数校验及格式化 | 按功能提取复用，先清理过期字段与引用 | `packages/types/`、`src/api/contracts.ts`、`src/utils/` |
| 页面布局、MUI 组件、路由 | 用小程序页面与组件重做 | 当前使用 React Router、MUI 与浏览器 DOM |
| 网络请求、会话、缓存 | 新建小程序适配层 | `HttpTransport` 使用 fetch、浏览器 Cookie、Web Locks |
| 商品图片 | 补真实选图与上传链路 | `ProductForm` 明确只支持预置图片，后端尚未发现上传实现 |

现有文档有历史订单、预约面交和交易评价的说明。迁移以当前代码及 `docs/contact-display-model.md` 为准：商品展示 → 联系申请或公开联系方式 → 双方自行联系。第一版沿用此流程。

## 第一版功能范围

底部入口建议为「集市 / 发布 / 通知 / 我的」。

- 集市：首页直接显示商品；分类、关键词、价格、成色、校区、楼栋筛选；分页加载与下拉刷新。
- 商品详情：真实图片、价格、成色、描述、卖家资料、收藏及联系申请。联系方式是否返回仍由后端授权。
- 发布：拍照或相册选图、上传、填写信息、选择是否公开联系方式、发布和编辑。
- 通知：收到及发出的联系申请、卖家同意或拒绝、申请状态刷新。若首版需要站内聊天，作为独立工作项接入现有会话接口。
- 我的：学校及校区资料、我的发布、收藏、联系申请、下架与标记已售、退出登录。
- 基本举报入口继续接现有后端和 Web 后台，避免迁移时丢失商品反馈渠道。

课程教材、圈子完整管理、求购订阅、批量发布、整套打包、协助整理及工作人员页面放在后续阶段，采用独立页面或分包逐项迁移。

## 登录与学校信息

当前 Web 认证使用内存 Access Token + HttpOnly 刷新 Cookie。后端业务请求通过 Bearer Token 验证会话，因此业务接口可以继续使用；小程序需要独立的登录恢复与退出流程。

推荐新增微信登录适配：小程序取得登录 code，后端与微信服务交换身份信息，再建立平台会话。AppSecret 仅保存在后端配置中，不写入小程序、共享代码或仓库。

微信身份通过独立映射关联平台用户，按 `appid + openid` 唯一约束；关联现有账号时必须验证该平台账号的控制权。不能按昵称、联系方式或用户自己提交的 openid 直接合并账号。

未关联用户先完成平台资料与学校选择，再允许访问同校商品。微信登录不代表学校或学籍已经验证，学校与圈子可见性仍由后端决定。

第一版优先在冷启动与会话到期时通过微信登录重新签发访问令牌，访问令牌留在内存。明确实现小程序会话撤销，保留 Web 当前的 Cookie 认证行为。上线前验证微信身份关联、重新登录、限流、退出及被限制用户的行为。

## 图片上传

用 `Taro.chooseMedia` 选择照片或拍照，上传成功后将持久化图片地址提交给现有商品接口；本地临时路径不能作为商品图片保存。官方参考：[chooseMedia](https://docs.taro.zone/docs/apis/media/video/chooseMedia)。

后端需增加受认证保护的图片上传或限时上传授权，并接入选定的存储服务。发布只接受当前用户有权使用的图片资源，同时处理文件大小、数量、失败重试及未发布图片清理。第一版沿用现有最多 5 张图片的限制。

具体存储服务和上传接口在实施时确定；现有的预置图片选择器不计为已完成真实上传。

## 页面和运行环境适配

- 使用 `View`、`Text`、`Image` 等小程序组件；保留深绿与浅底配色、两列商品卡片，减少桌面悬停和 3D 效果。
- React Router 改为小程序页面路由，商品 ID 和登录后返回位置通过页面参数传递。
- 通过小程序网络 API 实现请求层，保留响应 envelope、请求错误、超时、401 恢复和 429 提示；写操作恢复时不得重复创建商品或联系申请。
- 本地缓存改用小程序存储 API；平台资料以服务器为准，缓存不作为学校、角色或联系方式授权的依据。
- 页面再次显示时刷新联系申请与未读数据，隐藏或卸载时停止轮询，避免直接复制 Web 的常驻定时器。
- 商品分享进入详情后仍需走登录和学校可见性检查，分享路径不能绕过授权。

| 3. 发布与联系 | 真实图片上传、发布编辑、收藏、联系申请审批、我的发布、举报入口 | 高 |

可靠的工期需要在工程和接口验证后估算。当前不能把完整迁移视为修改配置后直接打包：页面要适配，认证与真实上传需要开发；此前 Web 完整类型检查也存在未清理的旧接口引用。

## 实施所需配置与完成标准

工程搭建和演示页面可以先做。微信身份联调需要真实小程序 AppID、后端私有 AppSecret 配置、可访问的后端环境；体验版与发布还需要在微信后台完成相应域名及应用配置。密钥不通过聊天或源代码传递。

第一版完成标准是：用户能在真机登录、只浏览有权查看的本校商品、上传真实照片并发布、申请联系、由卖家批准后查看联系方式，以及管理自己的发布和收藏。能编译或在开发工具中展示静态页面不代表迁移完成。
