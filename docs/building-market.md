# 楼栋集市：产品规则、数据模型与隐私边界

本文档说明模块 1「楼栋集市、最近排序与稳定面交点」的设计。实现与测试以此为准。

---

## 1. 产品目标

校园二手交易里最常见的问题是：能不能楼下自提？

在此之前，系统只知道「校区」。同一个校区里，隔着一公里的两栋楼，和同一栋楼，
在界面上看起来没有任何区别。楼栋集市补上了楼栋这一级，带来三个能力：

1. **只看本楼**：首页常驻开关，结果为空时自动逐级放宽范围。
2. **最近排序**：按与你宿舍楼的近似直线距离排序。
3. **校园示意地图**：在预约面交时展示楼栋与稳定面交点的相对位置，并推荐一个面交点。

## 2. 数据模型（V3）

迁移文件：`campus-market-backend/src/main/resources/db/migration/V3__building_market.sql`

### 2.1 `buildings`

| 列 | 类型 | 约束 |
| --- | --- | --- |
| `id` | `text` | 主键。与 `schools` / `campuses` / `meeting_points` 的主键类型一致 |
| `campus_id` | `text` | 外键 → `campuses(id)` |
| `zone` | `text` | 园区，非空白 |
| `name` | `text` | 楼栋名，非空白；`(campus_id, name)` 唯一 |
| `latitude` | `double precision` | 可空，`[-90, 90]` |
| `longitude` | `double precision` | 可空，`[-180, 180]` |
| `active` | `boolean` | 默认 `true` |
| `sort_order` | `integer` | 默认 0，非负 |
| `created_at` | `timestamptz` | 默认 `now()` |

**为什么主键是 `text`**：现有参考数据的主键都是 `text`，`users.campus` 与 `products.campus` 也是
`text` 外键。改用 `uuid` 或 `bigint` 会让每一处 JOIN 都需要显式转换。

**为什么楼号在校区内连续编号**：约束是「同一校区内楼栋名唯一」。演示数据里沁园是 1～3 号楼、
松园是 4～5 号楼，而不是两个园区各有一个「1号楼」。这也符合现实习惯，避免有人走错楼。

**停用而非删除**：楼栋一旦被商品或用户资料引用，就不能物理删除（外键会拒绝）。
需要下线时设置 `active = false`：它不再出现在可选列表中，旧商品仍能正常显示楼栋名。

### 2.2 关联字段

| 字段 | 说明 |
| --- | --- |
| `users.dorm_building_id` | 宿舍楼。可空，**由用户自己填写，系统绝不推断** |
| `products.building_id` | 取货楼栋。可空，公共地点交易或旧商品都没有楼栋 |

V3 **不会**替任何旧用户填写宿舍楼，也**不会**给任何旧商品分配楼栋。
旧的 `campus` 字段全部保留。

### 2.3 `meeting_points` 坐标

V3 为既有的 12 个稳定面交点（4 个校区 × 图书馆 / 食堂 / 快递站）补充了 `latitude` / `longitude`。

### 2.4 新增索引

| 索引 | 用途 |
| --- | --- |
| `buildings_campus_active_sort` | 按校区列出可选楼栋 |
| `buildings_campus_zone` | 同园区降级时收敛候选楼栋 |
| `products_building_status` | 本楼商品查询 |
| `users_dorm_building` | 外键列索引，避免楼栋停用检查退化为全表扫描 |
| `meeting_points_campus` | 按校区列出面交点 |

## 3. API

### 3.1 `GET /v1/buildings?campus={campus}[&zone={zone}]`

公共只读，未登录可访问。只返回 `active = true` 的楼栋，按 `zone → sort_order → name → id` 排序。
文本列使用 `COLLATE "C"`（Unicode 码点序），因此顺序与数据库 locale 无关（1.7A）：
「松」U+677E 小于「沁」U+6C81，所以东校区是松园在前。前端 Mock 用相同的码点比较。

返回字段：`id`、`campusId`、`zone`、`name`、`latitude`、`longitude`。
**不含任何住户数量或用户信息。**

### 3.2 `PATCH /v1/auth/me` 新增 `dormBuildingId`

| 情况 | 结果 |
| --- | --- |
| 同校区、启用中的楼栋 | 200 |
| 传 `null` 或空串 | 200，清空宿舍楼 |
| 楼栋不存在 | 404 |
| 楼栋已停用 | 400 |
| 楼栋不属于该校区 | 400 |
| 同时修改 `campus` 与 `dormBuildingId` | 按**新**校区校验 |

`dormBuildingId` 只出现在本人的 `/v1/auth/me`。

### 3.3 商品创建 / 更新新增 `buildingId`

校验规则与宿舍楼相同。商品投影新增 `buildingId`、`buildingName`、`buildingZone`；
没有楼栋时三者都是 `null`，前端回退显示校区。

**切换校区的固定语义**：只修改 `campus`、没有同时提供 `buildingId`，
而原楼栋不属于新校区时，返回 **400**。

之所以不静默清空：那会让买家在商品页上看到的取货点无声消失。
之所以不静默保留：那会让买家走到另一个校区去。这里要求卖家显式表态，
可以传新校区的楼栋，也可以传 `null` 表示不指定。

### 3.4 `GET /v1/products/feed`

楼栋集市专用端点。旧的 `GET /v1/products` **保持原样不变**。

之所以单独开端点：feed 需要返回范围元数据，往旧响应里塞字段看似兼容，
实际会让「这次到底用了哪个范围」变成隐式约定。

查询参数：`scope`（`BUILDING` / `ZONE` / `CAMPUS` / `SCHOOL`，默认 `SCHOOL`）、
`sort`（`latest` / `priceAsc` / `priceDesc` / `views` / `nearest`）、
以及与 `/v1/products` 相同的 `keyword`、`category`、`condition`、`minPrice`、`maxPrice`、`page`、`pageSize`。

响应：

```json
{
  "requestedScope": "BUILDING",
  "effectiveScope": "ZONE",
  "effectiveScopeLabel": "本园区",
  "fallbackApplied": true,
  "fallbackReason": "NO_RESULTS_IN_REQUESTED_SCOPE",
  "items": [
    { "...商品字段": "...", "sameBuilding": false,
      "approximateDistanceMeters": 100, "approximateWalkMinutes": 2 }
  ],
  "total": 1, "page": 1, "pageSize": 20
}
```

`fallbackReason` 是机器可读的原因码；前端据此组织文案，**不解析中文**。

错误：

| 情况 | 状态码 |
| --- | --- |
| 未登录请求 `BUILDING` / `ZONE` / `nearest` | 401 |
| 已登录但未设置宿舍楼 | 409 |
| 宿舍楼已被停用 | 409（要求重新选择，不静默退回校区） |

## 4. 降级规则

仅当 `scope = BUILDING`（用户主动开启「只看本楼」）时才降级，顺序固定：

```
本楼 → 同园区 → 同校区 → 全校
```

取第一个**有结果**的范围。全校也没有结果时，返回真正的空列表。

三条不可让步的约束：

1. **只在用户主动开启本楼时降级。** 普通浏览（`CAMPUS` / `SCHOOL`）为空就是空，
   不擅自扩大用户明确选择的范围。
2. **只放宽地理范围。** 关键词、分类、价格、成色逐条保留。本楼没有「数码电子」时，
   应该去同园区找「数码电子」，而不是拿别的分类凑数。
3. **范围在分页之前选定。** 选择依据是每个范围的**总数**，不是某一页的内容。
   否则翻到第二页时，会因为「这一页碰巧为空」而莫名其妙地扩大范围。

**唯一定义**：后端 `BuildingScope` 枚举；前端 `src/utils/geo.ts` 的 `SCOPE_FALLBACK_ORDER`。
Mock 与 REST 共用前端这一份，并有源码级测试确保它只被定义一次。

## 5. 距离与步行时间

- 公式：Haversine，地球半径 6371000 米。后端在 SQL 中计算，前端 `utils/geo.ts` 有等价实现，
  双方对同一组演示坐标的结果有对照测试。
- 步行速度：80 米/分钟，向上取整，至少 1 分钟。
- **同楼栋显示「同楼栋」**，不显示距离，也不显示「0 分钟」这种假精确的导航结果。
- 缺坐标时距离为 `null`，而不是 0。「不知道多远」和「就在眼前」是两件事。

**所有距离都是基于楼栋公共中心点的直线估算，不是导航距离，实际路线以校园道路为准。**

未引入 PostGIS：当前只需要几百米量级的粗略估算，引入扩展的代价远大于收益。

### 最近排序

1. 同楼栋
2. 近似直线距离升序
3. `created_at` 降序
4. `id`（保证同一查询的顺序稳定，可安全分页）

没有楼栋的商品排在所有有楼栋的商品之后。

## 6. 校园示意地图与面交点推荐

- 轻量 SVG，**不接入任何需要 API Key 的第三方地图，不加载地图 SDK**。
- **不调用 `navigator.geolocation`**。位置只来自用户自己填写的宿舍楼。
- 推荐逻辑：买家楼栋到面交点的距离 + 商品楼栋到面交点的距离，取两者之和最小；
  距离相同时按 id 稳定排序。
- 任一楼栋缺坐标时**不做伪精确推荐**，按原有顺序列出面交点，并说明原因。
- **推荐只是建议。** 打开预约弹窗时不预选任何面交点，最终地点必须由用户自己点选并提交。

推荐算法只在前端 `utils/geo.ts` 实现一次，Mock 与 REST 共用。

## 7. 隐私边界

| 规则 | 如何保证 |
| --- | --- |
| 宿舍楼只对本人可见 | `DomainMapper.user(row, privateFields=false)` 不输出该字段；前端 `PublicUser` 类型剔除该字段；`BuildingMarketIT` 第 9 项覆盖公共用户接口、商品详情、评论三处 |
| 商品卡片展示的是**商品的取货楼栋** | 来自商品记录本身，从不读取卖家资料 |
| 不收集房间号 / 楼层 / 床位 | 白名单拒绝这类字段；数据库中不存在这类列；前端源码扫描测试 |
| 不使用实时定位 | 前端源码扫描测试禁止 geolocation 调用 |
| 系统不推断宿舍楼 | V3 迁移与 Mock v3 迁移都有「不填充任何关联」的测试 |
| 发布页预填宿舍楼不等于静默公开 | 表单下方明确写出「买家会在商品页看到：某某楼」，用户可以改为「不指定楼栋」 |

## 8. 演示数据声明

V3 中的 20 栋楼、8 个园区与 12 个面交点坐标**全部是虚构的演示数据**：
以 (31.0000, 121.0000) 为原点按校区和园区偏移，不对应任何真实校园，
未使用任何真实高校的宿舍信息，也**不是真实校园导航数据**。

## 9. 替换为学校授权的真实楼栋数据

1. 从学校后勤或信息化部门取得**已授权公开**的楼栋名单与楼栋中心点坐标。
   只需要楼栋级别，不需要也不应索取房间或住户信息。
2. 新增 `V4__<描述>.sql`：
   - 用 `INSERT` 写入真实楼栋；
   - 对不再使用的演示楼栋执行 `UPDATE buildings SET active = false`，**不要 `DELETE`**
     （它们可能已被商品引用）；
   - 用 `UPDATE meeting_points` 替换面交点坐标。
3. **不要修改 V3**。V3 已在各环境执行过，修改会导致 Flyway 校验失败。
4. 真实数据上线后，更新本文件第 8 节的声明。

## 10. 已知局限

- 距离是直线估算。有河流、围墙或需要绕行的校园里，实际步行时间可能明显更长。
- Mock 的演示楼栋没有「停用」状态，停用相关行为只在 REST 模式下可验证。
- ~~园区之间的排列先后取决于数据库的排序规则~~（1.7A 已固定为码点序，见 3.1）。
