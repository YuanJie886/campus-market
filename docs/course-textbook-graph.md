# 课程教材图谱（模块 4）

课程 → 正确的教材版本 → 本校在售商品 → 按楼栋距离排序 → 无货时订阅这个版本 → 有新货同步命中。

> **当前目录是演示数据。** 课程名都带「演示课程」前缀，教师标签是「演示教师甲 / 乙 / 丙 / 丁」。
> 演示教材一律**无 ISBN**，用书目信息指纹去重，不占用任何真实书号。数据全部虚构，不代表任何真实学校，也不来自任何教务系统。
>
> **4.8 更正**：V6 最初给 5 本演示教材用了 979-0 开头的号码。979-0 是乐谱号（ISMN）号段，不是图书 ISBN，
> 把它当 ISBN 展示是错误的。V7 把这 5 条改为「无 ISBN」（只改逐项精确匹配的演示行），服务端与前端的 ISBN 解析也都拒绝 979-0 开头的号码。
> 无 ISBN 的版本不能按 ISBN 查找，可以从教材版本页的「我有这一版，去发布」进入发布页，仍需卖家在确认框里主动确认关联。

## 1. 为什么不依赖课程表接口

- 各校教务系统接口不统一、权限严格，接入周期往往以学期计。依赖它，这个功能就会被外部系统卡死。
- 课表里有学生名单、选课记录、班级成员、上课时间与教室，这些都是本项目**不需要、也不应该持有**的个人信息。
- 用户真正需要的只是一条可验证的关系：「这门课这个学期用哪一版教材」。这条关系可以由可信的数据维护者单独录入，不必读取任何个人课表。

因此本模块只实现「课程—开课—教材版本—商品」的关系，**不**读取学生课程表，**不**导入学生名单，**不**替用户生成选课记录。

## 2. 数据模型（V6）

迁移：`campus-market-backend/src/main/resources/db/migration/V6__course_textbook_graph.sql`（V1～V5 未改动，checksum 已验证不变）。

```
schools ─┬─ courses ── course_offerings ──┐
         │                                ├── course_textbooks（VERIFIED 才公开）
         └─ textbook_editions ────────────┘
                   │
                   ├── product_textbook_details ── products（只允许「教材书籍」分类）
                   └── demand_subscriptions.textbook_edition_id（精确版本订阅）
textbook_suggestions：普通用户的建议，永远是 PENDING / WITHDRAWN，不进入上面任何一张公开表
```

| 表 | 要点 |
|---|---|
| `courses` | 属于学校；`(school_id, normalized_name)` 唯一；课程代码可空，有则同校唯一；不存学生名单或班级成员 |
| `course_offerings` | 学年 `YYYY-YYYY`（后一年紧接前一年）；学期只能是 `SPRING / SUMMER / AUTUMN / WINTER`；开课校区与课程学校一致（复合外键）；同课程 + 学年 + 学期 + 教师标签防重复；教师只是公开的文字标签，不能包含数字或 `@`，不建立账号 |
| `textbook_editions` | 按学校划分的教材目录；`(school_id, normalized_isbn)` 唯一；ISBN 与「无 ISBN 指纹」恰好二选一；封面只允许 `https://`；`work_key` 是人工整理的同一部教材分组键 |
| `course_textbooks` | 用途 `REQUIRED / RECOMMENDED / REFERENCE`；状态 `VERIFIED / PENDING / REJECTED`；两端必须同校；公开目录只读 `VERIFIED` |
| `textbook_suggestions` | 状态**只有** `PENDING / WITHDRAWN`（没有 VERIFIED）；同一用户的相同待审核建议唯一 |
| `product_textbook_details` | 一件商品至多一个版本；只允许教材书籍分类；学校必须与商品校区的学校一致；保存关联当时的 ISBN / 书名 / 版次 / 出版社快照；版本不变时快照不可改写（触发器） |
| `demand_subscriptions.textbook_edition_id` | 版本必须同校（复合外键）；这类订阅分类固定为教材书籍、不带关键词；同一用户同一版本只能有一条启用订阅 |
| `demand_matches` 理由码约束 | 新增 `TEXTBOOK_EXACT`。V4 的内联 CHECK 按定义内容定位后替换，不依赖系统生成的约束名 |

## 3. ISBN 规范化与校验

同一套规则有三份实现：服务端 `textbook/Isbn.java`、数据库函数 `isbn13_is_valid / isbn10_is_valid / isbn10_to_isbn13`（在 CHECK 中使用）、前端 `utils/isbn.ts`。前后端用同一组号码做对照测试。

1. 去掉所有空白与连字符（半角 `-`、全角 `－`、各种破折号），末位 `x` 转成 `X`。
2. **10 位**：前 9 位是数字，末位是数字或 X；按权重 10…1 加权求和，结果能被 11 整除。
3. **13 位**：以 978 或 979 开头；按 1、3 交替加权求和，结果能被 10 整除。**979-0 开头的是乐谱号（ISMN），不是图书 ISBN，拒绝**（4.8；由 `Isbn.java` 与 `utils/isbn.ts` 执行，V6 的 SQL 函数只校验格式）。
4. 规范形式一律是 ISBN-13：ISBN-10 加 978 前缀后重新计算校验位。
5. 前端只做即时提示，**服务端和数据库才是最终权威**。

没有 ISBN 的教材（讲义、自编教材）使用元数据指纹：书名、作者、出版方、版次、年份规范化后做 SHA-256。任何一个字段不同，指纹就不同。它只用来防止明显的重复，**从不**用来把商品自动关联到某个版本。

## 4. 精确版本与「其他版本」

- **精确版本**：商品关联的 `textbook_edition_id` 与课程指定的版本 id 完全相等。
- **其他版本**：同一 `work_key` 下的其他版次（例如第 7 版与第 8 版）。`work_key` 是整理目录时人工给出的，**不是**从书名推断的。
- 教材详情接口用两个独立字段返回：`listings`（精确版本）和 `otherEditionListings`（其他版本），分别查询，从不混在一起排序。页面上「其他版本」放在单独的、带醒目边框的区域，标题是「其他版本（不是这个版本）」，并提示先确认课程是否接受。
- 精确版本的商品流沿用楼栋集市的排序：设置了宿舍楼时按直线距离由近到远（同一套 Haversine 公式），否则按最新发布。
- 标题相似但没有关联版本的商品，**不会**出现在任何版本的商品流里。

## 5. 商品发布与编辑

- 只有选择「教材书籍」分类时才显示 ISBN 输入。
- 卖家输入 ISBN（可以带空格或连字符）后，在本校目录中查找。命中后弹出确认框，写出书名、版次、ISBN、作者、出版社，**必须由卖家主动点「确认关联这个版本」**。系统从不自动绑定。
- 目录中没有这个 ISBN 时，可以不关联教材目录，照常发布。
- 非教材分类提交 `textbookEditionId` 返回 400；他校或不存在的版本返回 404；`schoolId`、各种快照字段、`sellerId` 等未知字段一律返回 400，错误响应带 `requestId`。
- 编辑时：再次提交同一版本不改写快照；换成另一个版本会整体替换快照，界面提示「买家看到的教材版本信息会随之变化」；切到其他分类时自动解除关联；显式提交 `null` 也会解除关联。已生成的订单验货快照不受影响（有测试断言）。
- 商品卡片和详情页写出具体版本：版次、出版社、ISBN、关联课程，而不是只写「高数教材」。卡片上的教材摘要与商品列表在同一条 SQL 里取回，不会逐条查询。

## 6. 教材建议（没有管理员后台）

- `POST /v1/textbook-suggestions`：建议某个开课学期使用某个版本。可以是目录中已有的版本、一个 ISBN，或者一份待审核的书目信息。没有 ISBN 时，书名、出版社、版次都必须填写。
- 默认且只能是 `PENDING`。只有提交人本人能看到（`GET /v1/textbook-suggestions/mine`）和撤回（`DELETE`，幂等），其他人一律 404。
- **不会**出现在公开课程页，**不会**自动变成 VERIFIED，没有「N 人认证即通过」，也不展示审核进度。
- 同一用户的相同建议幂等：重复提交返回原记录，不计入限额。每人每天最多 10 条新建议，复用 `rate_limit_counters`（`textbook_suggestion` 作用域）。
- **正式上线前**需要一个可信的数据审核入口（学校或课程负责人维护），由它把建议转成 `course_textbooks` 的 VERIFIED 关系。本阶段刻意不实现管理员系统。

## 7. 需求雷达联动

- 课程页或教材页没货时，可以「订阅这个教材版本」。服务端设定分类为教材书籍、学校为本人学校；用户只选地理范围和可选预算。
- 匹配是**精确版本 id 相等**，不看书名：相似书名、其他版次、卖家自己的订阅都不会命中。
- 商品在发布或编辑的同一事务里同步匹配。解除关联后原匹配失效；重新关联后恢复**同一条**匹配，不重复插入。
- 理由码 `TEXTBOOK_EXACT` 计 50 分，排在理由列表第一位，替代关键词理由（教材订阅不带关键词，由数据库约束保证）。总分上限仍是 100；档位（tier）只由服务端给出，前端只翻译理由码。
- 兼容性：没有教材版本的订阅，指纹规范串与 V4 时代**逐字节相同**；关键词订阅的匹配行为不变（有测试断言）。
- 候选查询分两路（UNION ALL）。普通订阅走新的部分索引 `demand_subscriptions_match_plain`，这个索引不含教材订阅；教材订阅按版本 id 走 `demand_subscriptions_match_textbook`。这样每发布一件教材商品，不会把全校的教材订阅都扫一遍（执行计划见 `TextbookPerformanceIT`）。

## 8. 隐私边界

- 课程与教材接口只返回目录数据，以及在售商品的非本人视角投影（不含卖家联系方式）。
- 不返回订阅者、等待人数、购买者、宿舍楼归属，也不返回 PENDING 建议或它们的提交人。在售数量只是一个聚合数字。
- 所有接口都需要登录。学校只由登录用户的校区推导；他校的课程、开课、版本、ISBN 一律返回 404，不区分「不存在」和「不属于你的学校」，避免被枚举。
- 不申请相机、定位或通知权限：ISBN 只能手动输入。
- 选课和 ISBN 都不会被包装成「教务认证」。界面不出现「已认证」「官方认证」「审核进度」一类说法（源码扫描保护）。

## 10. 后续接入真实学校数据的流程（本阶段不实现）

1. 与学校确认数据来源和授权，只取「课程—开课—指定教材」这一层，不取学生数据。
2. 建立可信的维护入口（有身份核验的课程负责人或教务人员），并记录操作日志。
3. 把建议队列接到这个入口：审核通过后写入 `course_textbooks`（VERIFIED），驳回则记为 REJECTED。
4. 为真实学校新建 `schools` / `campuses` 行，把演示数据停用（`active = false`），不要物理删除。
5. 界面去掉演示提示前，确认 `is_demo = false` 的数据都来自上述可信流程。

## 11. 已知限制

- 课程名只做规范化后的子串匹配，不做拼音、同义词或分词。数据量很大时，子串搜索只能在学校范围内逐行比较（btree 索引帮不上忙），需要时可以引入 pg_trgm。
- 没有管理员与审核后台，所以建议永远停留在待审核状态。
- 教材目录按学校划分，同一 ISBN 在两所学校是两行，不跨校共享。
- 课程页的「查看在售」会跳转到教材版本页，不在课程页内联列出商品。
- 演示教材没有 ISBN（4.8 起）。早期版本曾用 979-0（ISMN）号段充当演示书号，这是错误的，已由 V7 更正。
- jsdom 无法验证颜色对比度，自动化无障碍检查通过不等于 WCAG 合规。
