## 6. 前端检查结果

### 6.1 Access Token 实际保存位置 —— 已确认存在问题

**保存在 `localStorage`，不是内存。**

`src/utils/tokenStore.ts:5`：

```ts
set(token: StoredToken): void { try { window.localStorage.setItem(KEY, JSON.stringify(token)) } catch { } }
```

key 为 `campus_market_access_token_v1`。全仓 `localStorage` 使用点仅 `src/utils/storage.ts` 与 `src/utils/tokenStore.ts` 两处，`tokenStore` 是唯一的令牌落盘点。

后果：任何 XSS 均可直接读取 15 分钟有效期的 access token。Refresh Token 用 HttpOnly Cookie 保护得当，但 access token 的保护等级被拉低到 `localStorage` 水平，`HttpOnly` 设计意图被部分抵消。详见 R-09。

### 6.2 401 自动刷新的并发去重 —— 已确认正常

`src/api/httpTransport.ts:24-44`：

```ts
private refreshing: Promise<void> | null = null;
private refresh(): Promise<void> {
  if (!this.refreshing) this.refreshing = this.request<AuthSession>('/v1/auth/refresh', { method: 'POST' }, false)
    .then(...).catch(...).finally(() => { this.refreshing = null });
  return this.refreshing;
}
```

- **并发去重成立**：多个并发 401 共享同一 `refreshing` Promise，只会触发一次 `/v1/auth/refresh`。
- **无限递归防护成立**：刷新请求本身以 `retry = false` 发出；重试调用亦为 `request(path, init, false)`。
- **路径豁免成立**：`/\/auth\/(login|register|refresh|logout)$/` 上的 401 不触发刷新。
- **失败清理成立**：刷新返回 401 时 `tokenStore.clear()`。

一个附带观察：`HttpTransport` 实例由 `client.ts` 单例持有，去重作用域覆盖整个应用，无多实例问题。

`RestCampusMarketApi.toggleFavorite()` 发出 `PUT /v1/products/{id}/favorite`，服务端 `MarketService.favorite()`：

```java
if (favorites.deleteByUserAndProduct(userId, productId) > 0) return map("active", false);
```

静态设计完整，但**无任何测试在真实 PostgreSQL 上验证其生效**（见 7.5 与第 9 章第 1、12 项）。

### 7.2 订单状态机实际规则

`OrderService.TRANSITIONS` 仅接受 4 个目标：`PENDING_MEETING`、`BUYER_CONFIRMED`、`COMPLETED`、`CANCELLED`。

| 目标状态 | 允许角色 | 要求前置状态 | 附加条件 |
|---|---|---|---|
| `PENDING_MEETING` | 仅卖家（`!buyer`） | `PENDING_SELLER_CONFIRM` | 同时把 `expires_at` 改为 `meetingAt + 1天` |
| `BUYER_CONFIRMED` | 仅买家（`buyer`） | `PENDING_MEETING` | — |
| `COMPLETED` | 仅卖家（`!buyer`） | `BUYER_CONFIRMED` | 必须提交正确的 6 位 `confirmationCode` |
| `CANCELLED` | 买家或卖家 | **仅** `PENDING_SELLER_CONFIRM` 或 `PENDING_MEETING` | 释放商品回「在售」 |

**订单取消的真实允许状态和角色（应答任务要求）：** 允许角色为**买卖双方任一**；允许前置状态**仅两个**——`PENDING_SELLER_CONFIRM` 与 `PENDING_MEETING`。一旦进入 `BUYER_CONFIRMED`，**任何角色都无法取消**。

`SELLER_CONFIRMED` 与 `DISPUTED` 虽在数据库 CHECK 约束与 `CanonicalOrderStatus` 类型中声明，但**永远不会成为 `orders.status` 的值**：`SELLER_CONFIRMED` 仅作为 `order_events` 的一条审计记录写入（`OrderService.java:81`），`DISPUTED` 无任何写入路径。

### 7.7 CORS 与注入防护

- **CORS**：`WebConfig` 对 `/**` 放行，`allowedOrigins(webOrigin)` 为**精确单一来源**（非通配），方法限 `GET/POST/PATCH/PUT/OPTIONS`，`allowCredentials(true)`，`maxAge 3600`。配置合理。
- **CSRF 缓解**：`refresh` / `logout` 额外校验 `Origin` 头必须等于 `WEB_ORIGIN`（`AuthService.checkOrigin`）。
- **SQL 注入**：`ProductMapper.xml` 使用 `ORDER BY ${orderBy}`（字符串拼接）。**经核验安全**——`MarketService.java:62` 用 `switch` 白名单将用户输入映射为固定 SQL 片段，非法值抛 400，用户输入不可能进入 `${}`。其余全部条件使用 `#{}` 预编译参数。

### 判断 4 —— 已确认存在问题

**结论：已确认存在问题（P0）**

`OrderService.java:75-80`：

```java
@Transactional
public Map<String, Object> transition(String uid, String orderId, Map<String, Object> body) {
    ...
    if ("COMPLETED".equals(to) && (order.getCodeAttempts() >= 5 || !order.getConfirmationCode().equals(confirmationCode))) {
        orders.incrementCodeAttempts(oid);
        throw ApiException.badRequest("确认码错误或已达 5 次上限，请联系运营人员处理");
    }
```

三项事实共同成立：

1. `transition()` 标注 `@Transactional`（`OrderService.java:75`）
2. `ApiException extends RuntimeException`（`ApiException.java:3`）
3. 全后端**未使用** `noRollbackFor`、`Propagation.REQUIRES_NEW` 或任何独立事务传播（全仓检索零命中）

Spring `@Transactional` 的默认回滚规则是「遇 `RuntimeException` 回滚」。因此 `orders.incrementCodeAttempts(oid)` 发出的 `UPDATE orders SET code_attempts=code_attempts+1` 与紧随其后的 `throw` 处于**同一事务**，异常触发回滚后该 UPDATE 被一并撤销。

**后果：`code_attempts` 永远停留在 0，`>= 5` 的锁死分支永远不可能命中。** 结合后端**完全没有限流**（全仓无 ratelimit / bucket4j / resilience4j），6 位确认码的 10⁶ 空间可被无限次尝试。由于提交确认码的角色是**卖家**，恶意卖家可绕过买家的当面核验，暴力破解后强制将订单推进至 `COMPLETED`、商品置为「已售出」并解锁双向评价——构成**强制成交**。

附带影响：`transition()` 开头调用的 `expire()` 也在同一事务内，任何 `transition` 抛异常都会连带回滚本次检测到的超时订单释放。`create()` 同理。

证据路径：`OrderService.java:75-80`、`ApiException.java:3`、`OrderMapper.java:22`

### 判断 6 —— 已确认存在问题

**结论：已确认存在问题（P1）**

`OrderService.java:78`：


取消的允许前置状态**仅** `PENDING_SELLER_CONFIRM` 与 `PENDING_MEETING`。一旦买家把订单推进到 `BUYER_CONFIRMED`，**买家和卖家都无法再取消**（抛 409「当前角色或订单状态不允许此操作」）。

单看这条规则是合理设计（防止买家确认后反悔）。但与判断 5 组合后产生不可恢复状态：

- `BUYER_CONFIRMED` 不被过期任务处理（判断 5）
- `BUYER_CONFIRMED` 不可取消（本判断）
- 唯一出口 `COMPLETED` 需要**卖家**提交正确确认码

因此只要卖家消极（失联、拒绝核销、确认码丢失），订单永久停留在 `BUYER_CONFIRMED`。由于部分唯一索引 `one_active_order_per_product` 把该状态视为「活跃」，**该商品永远无法被其他买家预约，卖家也无法编辑**（`MarketService.updateProduct` 对「预约中」商品直接抛 409）。商品进入永久死锁，且系统内**不存在任何管理员干预接口**。

证据路径：`OrderService.java:78`、`OrderMapper.java:19`、`db/schema.sql`（`one_active_order_per_product`）、`MarketService.updateProduct`

### 判断 7 —— 已确认正常

**结论：已确认正常**

`DomainMapper.order()` 是**全部**订单出口的唯一投影函数，第 113 行：

```java
if (viewer.equals(text(row.get("buyer_id")))) result.put("confirmationCode", text(row.get("confirmation_code")));
```

三条返回订单的路径均经此函数，且 `viewer` 一律来自 `auth.authenticate(request, false)` 的可信结果：

- `OrderService.create()` → `mapper.order(row, uid, ...)`

### 判断 9 —— 已确认存在问题

**结论：已确认存在问题（P2）**

`MarketService.favorite()`：

```java
@Transactional
public Map<String, Object> favorite(String uid, String id) {
    product(id, uid);
    UUID userId = uuid(uid), productId = uuid(id);
    if (favorites.deleteByUserAndProduct(userId, productId) > 0) return map("active", false);
    FavoriteEntity entity = new FavoriteEntity(); ... favorites.insert(entity); return map("active", true);
}
```

这是 **toggle 语义**：先尝试删除，删到了就返回 `active:false`，没删到才插入并返回 `active:true`。

对应的 HTTP 方法是 `PUT`（`CampusMarketController` `@PutMapping("/products/{id}/favorite")`，`restCampusMarketApi.ts` `this.transport.put(...)`）。RFC 9110 要求 `PUT` 幂等——重复发送同一请求，服务端状态应与发送一次相同。此处连续两次 `PUT` 会先收藏再取消，**状态与调用次数的奇偶性绑定**，明确违反幂等语义。

实际风险：用户双击、网络层重试、或前端 `HttpTransport` 的 401 重试路径（`httpTransport.ts:64-70`，若首次请求已在服务端生效但响应被判为 401）都会导致收藏状态与用户意图相反。

数据库层的 `UNIQUE(user_id, product_id)` 只防止重复行，无法纠正 toggle 语义本身。

证据路径：`MarketService.java`（`favorite` 方法）、`CampusMarketController.java:62`、`src/api/restCampusMarketApi.ts`（`toggleFavorite`）

### R-01 · P0 · 请求体可覆盖认证买家身份，构成越权代下单

**证据路径**：`campus-market-backend/src/main/java/com/lulu/campusmarketbackend/service/OrderService.java:58`

```java
UUID buyerId = uuid(body.getOrDefault("__buyerId", uid)), productId = uuid(body.get("productId"));
```

`uid` 来自 `auth.authenticate(request, false)`，是可信身份。但只要请求体携带 `__buyerId` 字段，它就会**覆盖**认证身份成为订单买家。全仓检索确认 `__buyerId` **仅在此一处出现**——前端从不发送，无任何测试使用，也没有任何注释说明其用途。

与之形成对比：`MarketService.createProduct` / `updateProduct` / `profile` 三处都实现了未知字段白名单（`if (body.keySet().stream().anyMatch(key -> !List.of(...).contains(key))) throw badRequest`），唯独 `OrderService.create()` **没有这层防护**。

**影响**：
- 任意已登录用户可用他人身份创建订单。受害者 ID 易于获取——`GET /v1/users/{id}` 公开，且商品响应直接暴露 `sellerId`。
- 可批量锁定任意在售商品（置为「预约中」），对平台构成库存封锁型破坏。
- 消耗受害者的 `(buyer_id, idempotency_key)` 唯一键空间。
- 受害者账户下出现从未下过的订单。
- 自购防护 `if (sellerId.toString().equals(uid))` 校验的是 `uid` 而非 `buyerId`，未覆盖此路径（数据库 `CHECK(buyer_id<>seller_id)` 可兜住 buyer==seller 的情形，但兜不住第三方冒用）。

**建议处理方式**：删除 `body.getOrDefault("__buyerId", uid)`，直接使用 `uid`；并为 `OrderService.create()` 补充与 `MarketService` 一致的未知字段白名单校验。若该字段确为测试遗留，应连同测试路径一并移除。

**是否阻塞下一模块**：**是**

### R-02 · P0 · 确认码尝试次数随异常回滚，5 次锁死失效，叠加无限流可暴力破解

**证据路径**：`OrderService.java:75-80`、`ApiException.java:3`、`OrderMapper.java:22`

详见第 9 章判断 4。核心链条：`@Transactional` + `ApiException extends RuntimeException` + 无 `noRollbackFor` / `REQUIRES_NEW` → `incrementCodeAttempts` 的 UPDATE 与抛出的异常同事务，回滚后计数归零。

**影响**：
- `code_attempts` 恒为 0，`>= 5` 的锁死分支**永不可达**，代码中的防暴力破解措施实际不存在。
- 后端**无任何限流**（全仓无 ratelimit / bucket4j / resilience4j 实现），6 位确认码的 10⁶ 空间可被无限次尝试。
- 提交确认码的角色是**卖家**，因此恶意卖家可绕过买家当面核验，强制把订单推进到 `COMPLETED`，商品置「已售出」并解锁双向评价——**构成强制成交**。
- 附带：`transition()` 与 `create()` 开头调用的 `expire()` 同处一个事务，任何异常都会连带回滚本次超时释放。

**建议处理方式**：将计数更新移出当前事务（`Propagation.REQUIRES_NEW` 的独立方法，或在 `ApiExceptionHandler` 之外的补偿路径写入）；同时对 `/v1/orders/{id}/transitions` 增加按订单与按 IP 的限流；并补充一个真实 PostgreSQL 环境下的回归测试覆盖「连错 5 次后锁死」。

### R-03 · P0 · 生产环境可使用仓库内公开的默认 JWT 密钥静默启动

**证据路径**：`campus-market-backend/src/main/resources/application.yaml:18`、`JwtService.java:33`

详见第 9 章判断 10。`jwt-secret` 内置 67 字符默认值，`JwtService` 仅校验 `length() < 32`，67 > 32 故校验通过，`JWT_SECRET` 未设置时**静默使用公开密钥启动，无任何告警**。

**影响**：任何能读到本仓库的人可离线签发任意 `sub` 的合法 access token，冒充任意用户——读取他人订单确认码、以他人身份下单、发送私信、修改资料。这直接使第 9 章判断 7 的确认码保护、以及全部基于 `uid` 的归属校验失效。

**建议处理方式**：移除 `application.yaml` 中的内置默认值，改为必填（`${JWT_SECRET}` 无 fallback，缺失即启动失败）；或在 `JwtService` 中增加「等于已知默认值则拒绝启动」的校验，仅在 `dev` profile 下放行。同时补齐 `deploy/.env` 的创建指引。

**是否阻塞下一模块**：**是**

### R-06 · P1 · `BUYER_CONFIRMED` 构成不可恢复终态，商品永久死锁
