本文件记录阶段 0.9（A–E）的改动、证据与仍然存在的局限。
基线风险编号沿用 `docs/audits/v1.1-baseline-audit.md`。

## 0.9A Access Token 仅存内存

### 改造前

`campus_market_access_token_v1` 存在 `localStorage`。任何一次 XSS 都能同步读走一枚
15 分钟内有效的访问令牌，而 `campus-market-backend/README.md` 当时声称它
「保存在前端内存中」——文档与实现不符（基线风险 R-09）。

### 改造后

- 新增 `src/utils/authTokenStore.ts`：令牌与 `expiresAt` 只活在模块闭包里，
  没有任何导出路径能把它写进 Web Storage、Cookie、URL 或 DOM。
- `expiresAt` **只**用于安排主动刷新，不参与任何权限判断；前端从不解析 JWT。
- 删除 `src/utils/tokenStore.ts`。
- 启动时调用 `purgeLegacyAuthTokens()` 逐个 `removeItem` 历史 key。
  刻意不用 `localStorage.clear()`：那会连带清掉 Mock 演示数据与筛选偏好。
  旧令牌的值不被读取、不被迁移——一枚已经落在磁盘上的凭据没有继续使用的价值。
- Mock 演示模式的登录态改存 `MockDatabase.currentUserId`，与真实认证彻底分家，
  离线演示刷新页面后仍保持登录。

### 页面刷新后的恢复路径

`src/utils/sessionRecovery.ts` 的 `recoverSession()` 携带 HttpOnly 的 `cm_refresh`
Cookie 调 `POST /v1/auth/refresh`。结果分四种，其中 401（未登录）与
503/网络失败（认证服务不可用）**严格区分**——把后者显示成「未登录」会让用户
反复重试登录，并掩盖真正的故障。

## 0.9B 刷新流程与 Cookie 加固

### 前端

| 机制 | 实现 | 位置 |
| --- | --- | --- |
| 单飞 | 并发 401 共享同一个刷新 Promise | `HttpTransport.refresh()` |
| 最多重试一次 | 递归调用传 `retry=false` | `HttpTransport.request()` |
| 主动刷新 | 过期前 60 秒，全局仅一个 timer，失败不重排 | `scheduleProactiveRefresh()` |
| 跨标签页 | Web Locks 串行化 | `withRefreshLock()` |
| 429 | **从不**自动重试 | `HttpTransport.request()` |

### 后端 Cookie

`RefreshCookieIT`（7 项）把属性钉死：`HttpOnly` + `SameSite=Strict` +
`Path=/v1/auth` + 正数 `Max-Age`；刷新令牌不出现在响应体中；刷新会轮换且旧值立即
失效；登出同时清 Cookie 与服务端会话。

### 关闭「静默的不安全默认值」

`SECURE_COOKIES` 默认 `false` 原本是为本地 http 开发服务的，但它静默地把生产也
置于风险中：忘记设置不会有任何征兆。现在两道闸门：

1. `deploy/docker-compose.yml` 改为 `${SECURE_COOKIES:?...}`，**没有默认值**，不填就起不来。
2. `AuthService` 构造期拒绝「`WEB_ORIGIN` 是 https 而 `SECURE_COOKIES=false`」的矛盾组合。
   http 本地开发仍然允许，只记一条启动 WARN。

### 诚实说明：跨标签页竞争未被完全消除

Web Locks 只在支持它的浏览器里生效；不支持时降级为「仅单标签页 single-flight」。
此外锁只覆盖本源页面，无法约束同时在跑的其他客户端。后端的轮换语义是最终防线
（`RefreshCookieIT` 第 4 项已验证：同一枚令牌只能兑换一次），但在降级场景下，
用户仍可能遇到一次需要重新登录的失败刷新。**这一点没有被解决，只是被限制了影响范围。**

## 0.9C 错误可追溯

- `logback-spring.xml`：日志模式加入 `[requestId=%X{requestId:--}]`，
  访问日志与响应头 `X-Request-ID` 同源（0.8B 的 `RequestIdFilter`）。
- `RequestIdIT` 第 4 项扩展到 400/401/404/409/429/500。
  500 通过**仅存在于 test source** 的 `/__test__/boom` 端点触发，生产构建里没有这个接口。
- 前端 `ApiError` 携带 `requestId` / `httpStatus` / `retryAfterSeconds`；
  `requestId` 优先取响应头，缺失时回落到 envelope。
- 新增 `toUserMessage()` 并替换全站 12 处 `(e as Error).message`。
  提示里带可复制的错误编号，但不含 Token、Cookie、stack 或原始响应体。

## 0.9D 路由懒加载与构建拆包

`chunkSizeWarningLimit` **保持 1500 未改动**（`vite.config.ts:17`）。

| 产物 | 改造前 | 改造后 |
| --- | --- | --- |
| chunk 数（JS） | 1 | 11 |
| 入口 JS | 598,977 B（gzip 188.91 kB） | 94,033 B（gzip ~31.3 kB） |
| 最大 chunk | 598,977 B（即入口） | 314,989 B（`vendor-mui`） |
| `vendor-react` | —（在入口内） | 164,326 B |
| `vendor-mui` | —（在入口内） | 314,989 B |
| 路由分片 | 无 | 8 个，549 B – 11,481 B |
| CSS | 43,762 B | 43,762 B |

- 目标「入口 chunk < 450 kB」已达成（94,033 B）。
- **但首屏关键路径的真实下降只有约 25.6 kB**（598,977 → 573,348 B，−4.3%）：
  vendor 分片仍然要在首屏加载，被移出关键路径的只有 8 个路由分片。
  vendor 拆分的主要收益是缓存粒度——业务代码每次发版都变，React / MUI 只在升级依赖时变。
  把入口 chunk 变小不等于用户少下载了同等字节，这里不做夸大。
- 现在**没有任何 chunk 超过 Vite 的默认 500 kB 阈值**（最大 314,989 B），
  即便把上限调回默认值也不会再告警。
- 首页与登录/注册留在首包：它们是冷启动落地页，懒加载只会给首屏多加一次往返。
- `RouteErrorBoundary` 兜住动态 import 失败（网络中断、发版后旧 chunk 失效），
  提供「重试 / 刷新页面」，而不是白屏。

## 0.9E Mock 数据 schema 版本化

- 负载新增 `schemaVersion`（当前 **2**），迁移在装载时一次性完成并落盘。
- v1→v2：为订单固化 `canonicalStatus`，并按订单重算商品状态。
- 歧义处理：中文「交易中」同时对应 `PENDING_MEETING` / `BUYER_CONFIRMED` /
  `SELLER_CONFIRMED` / `DISPUTED`。迁移保守取 `PENDING_MEETING`（状态机上最靠前、
  权限最小的那一个）并置 `legacyStatusAmbiguous: true`，界面显示提示请用户核对。
  **绝不猜成会放宽后续操作权限的状态。**
- 已有 `canonicalStatus` 的订单是真值来源，迁移不覆盖。
- 商品状态重算不碰「已下架」——那是卖家的显式决定，不是算出来的。
- 幂等：同一份负载连续迁移两次，第二次是空操作，结果逐字节一致。
- 读到**更高**版本时不降级、不写回，本次会话在内存里跑，避免旧代码毁掉新版数据。
- 损坏 / 形状不可识别的负载回退种子数据，不抛异常打断演示。
- 删除 `fromCanonicalStatus()`（与 `statusLabel()` 完全重复的废弃别名），
  并移除 `OrdersPage` 里残留的中文→canonical 反向映射。
