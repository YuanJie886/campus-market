# 交易承诺、防爽约与可信治理（模块 6.1 收口 + 模块 7 + 7.1 规则收口）

模块 7 解决三件事：下单后随意取消、约好面交后爽约、商品 / 圈子 / 用户违规没有平台处理入口。
同时收口模块 6 的三处遗留：学校隔离（6.1A）、邀请登录连续性（6.1B）、圈子成员分页与人数上限（6.1C）。

**平台边界（界面与文档里都这样写，不能越过）**：

- 平台**不托管资金**、不接支付、不收保证金；取消只是释放商品。
- 平台治理**不等于**交易仲裁或赔付，也不对商品真伪下结论——系统里没有这类动作。
- 没有公开的「信用分」；取消次数、爽约、限制都**不公开**，只给本人看。
- **单方报告不会自动处罚任何人**；手动声明的「已到达」**不是定位证据**。
- 所有处罚可解释（原因码）、有期限（最长 30 天，没有永久限制）、有审计（只增不改）、可申诉（每条一次）。

## 1. 模块 6.1

### 1.1 学校隔离（6.1A）

「PUBLIC」表示**当前学校**公开，不表示整个部署实例公开。采用推荐方案：

- 未登录只能看到落地页与登录注册；商品列表、搜索、feed、详情、评论、浏览计数、他人资料与公共履历都需要登录（401）。
  楼栋、面交点、验货模板等非用户数据保持公开。
- 学校永远由认证用户所在校区推导（`SchoolScope`）；请求里出现 `schoolId / school / school_id` 一律 400。
  校区合法性以数据库 `campuses` 表为准，不再硬编码校区名单，多校部署只需登记校区。
- 读取侧：V10 重新定义权威可见性函数 `product_visible_to / product_readable_by`（6 参数版本），加入「商品校区属于查看者学校」与
  「被治理隐藏的商品只有卖家看得到」；V9 的 4 参数版本改为委托给新版本。列表、计数、feed、收藏、需求匹配、收件箱、未读数、
  教材在售数全部走这两个函数，他校商品直接 ID 访问与不存在同为 404。下单（`ProductVisibility.requirePurchasable`）同样检查学校与隐藏状态。
- 写入侧：发布、改校区、改资料、草稿只能使用本校校区；V10 触发器兜底——商品校区必须与卖家同校、新订单买家必须与商品同校。
- 已成立的订单不受影响：订单参与者例外仍然只针对那一件商品。

测试：`SchoolIsolationIT`（两所学校：未登录 401、列表 / 总数 / feed 不跨校、他校详情 / 评论 / 收藏 / 会话 / 下单 / 资料 / 履历 404、
schoolId 400、写入不能跨校、需求雷达不跨校、数据库兜底），前端 `governance.contract.test.ts`（Mock 同样规则）。

### 1.2 邀请登录连续性（6.1B）

未登录打开 `/circles/join#code=…`：

1. 邀请页（不再被登录拦截吞掉）读取 `#` 里的邀请码，**立即** `history.replaceState` 清除地址栏；
2. 邀请码只保存在当前页面进程的内存里（`utils/pendingInvite.ts` 的模块变量）：不写 localStorage / sessionStorage / Cookie，
   不进 URL query，不写日志；每个标签页各有一份，互不传播；
3. 登录或注册成功后回到邀请页并自动填入，**仍需用户点击「加入」才会兑换**，不会登录即自动加入；
4. 登录 / 注册失败、离开登录流程、退出登录、成功加入后立即清除；刷新页面后丢失——这是刻意的安全取舍，页面会提前说明；
5. 错误邀请码仍是统一 404，兑换照常限流。

测试：`inviteContinuity.test.tsx`（完整流程、地址栏立即清除、存储 / Cookie / 日志无邀请码、失败清除、离开流程清除、退出清除、
刷新不恢复、另一标签页拿不到、统一 404 与 429）。

### 1.3 成员分页与人数上限（6.1C）

- `GET /v1/circles/{id}/members?page=&size=`：默认 20、最大 100；稳定排序「角色优先级 → 加入时间 → userId」；返回 `total/page/size`；
  只有 OWNER / MODERATOR 可访问（普通成员 403、非成员与他校 404）；投影仍只有昵称、头像、角色、加入时间。
- 单圈在籍成员上限 1000（含 OWNER；LEFT / REMOVED 不占名额；重新加入重新检查）：兑换时在圈子行锁下计数，满员 409 且邀请码不被消耗；
  V10 触发器 `circle_member_cap_guard` 先锁圈子行再计数，绕过接口也不能超限。已在籍的人再次兑换是幂等的：返回圈子，不消耗邀请码、不占名额。
- 管理页分页加载，不一次加载全部成员。
- 索引 `circle_memberships_page (circle_id, circle_role_rank(role), joined_at, user_id) INCLUDE (role) WHERE status='ACTIVE'`：
  分页子查询只读索引取出一页，再按主键连接 `users`；1000 人圈子的首页与第 40 页都是 Index Only Scan，语句条数与页大小无关（`CirclePerformanceIT` 7）。

测试：`CircleMemberLimitIT`（分页、上限、并发抢名额）、`memberPaging.test.tsx`。

## 3. 数据模型（V10）

| 表 | 要点 |
|---|---|
| `order_cancellations` | 主键就是订单（一张订单至多一条，幂等）；阶段、原因、执行人、时间都由服务端写入；与取消状态变化同一事务；只能在订单已取消时写入、执行人必须是订单一方；只增不改 |
| `order_no_show_reports` | 必须在订单双方之间、以 PENDING 开始；同一订单 + 档期版本 + 被报告人最多一条有效报告；状态机由触发器保证；`confirmed_at` 用于 30 天窗口 |
| `staff_members` | 默认为空；学校必须等于本人所在学校；不能删除（停用 `active=false`） |
| `moderation_cases` | 同一学校同一目标同时只有一个未结案件；结果写入后不能更换、不能改回待处理 |
| `moderation_reports` | 同一人对同一目标只保留一份；必要快照（例如那一条消息的正文）；只增不改 |
| `moderation_actions` | 每个动作的工作人员、原因码、说明、期限、是否实际生效；只增不改 |
| `moderation_appeals` | 每条限制 / 每次处理只能申诉一次；只能决定一次；内容不可改 |
| `user_restrictions` | 范围 BOOKING / PUBLISHING / CIRCLE_CREATION；1～720 小时（最长 30 天）；来源：某个案件的工作人员决定，或确认爽约后的公开规则；只能撤销一次，不能删除 |

迁移只加结构：不植入工作人员、举报、案件、处罚或爽约；旧的已取消订单不补写取消原因（`FlywayLegacyBaselineIT` 场景 J）。

## 4. 取消、爽约与争议的区别

| | 取消 | 爽约 | 争议（验货不一致） |
|---|---|---|---|
| 是什么 | 一方决定不继续这笔交易 | 双方确认过的档期，一方没有出现 | 双方见面验货，结果与卖家声明不一致 |
| 谁发起 | 订单任一方（按状态机） | 订单任一方报告对方 | 买家提交验货 |
| 是否处罚 | 从不自动处罚 | 只有对方承认或工作人员确认后按规则计数 | 不处罚，只能取消 |
| 谁看得到 | 订单双方；确认档期后的取消出现在本人履历 | 订单双方与复核的工作人员 | 订单双方 |

### 4.1 取消

- 卖家确认前：买家可以无责取消，原因选填；仍然记录取消事实（阶段 BEFORE_SELLER_CONFIRM）。卖家拒绝或不处理继续使用原来的过期机制。
- 卖家确认后：双方仍可取消，但必须选择 `CHANGED_MIND / SCHEDULE_CONFLICT / ITEM_UNAVAILABLE / CONDITION_MISMATCH / COUNTERPART_UNRESPONSIVE / OTHER`，
  「其他」必须写说明（≤ 200 字，不接受 HTML）。不自动处罚。
- 阶段由服务端判定：`BEFORE_SELLER_CONFIRM`、`AFTER_SELLER_CONFIRM`（卖家接单即同意买家下单时的原始预约）、`AFTER_MEETING_AGREED`
  （双方通过改约握手确认过档期）、`AFTER_ARRIVAL_REPORTED`（当前档期有一方声明已到达）、`INSPECTION_MISMATCH`。
- 幂等：订单已取消时（包括双方同时取消），重复请求返回同一结果，不重复记录。
- 已确认档期后的取消出现在本人履历（`/me/trade-history` 的 `cancellationsAfterAgreement`），不进入公共履历。

### 4.2 爽约报告

- 必须存在双方确认过、**有明确开始与结束时间**的档期快照（7.1A，见第 13 节）；只能在快照结束 15 分钟后、7 天内提交；只能报告订单对方（服务端推导，客户端不能指定）；
  已经见面（验货提交 / 买家确认 / 核销）或在档期之前已经取消的订单不能报告。
- 单方报告只是 **PENDING**，不产生任何处罚、不公开。对方可以**承认**（ACKNOWLEDGED，计为已确认）或**提出异议**（DISPUTED，自动进入工作人员复核）；
  报告人也可以请工作人员复核。工作人员复核后 CONFIRMED 或 REJECTED。
- 改约生效后，旧档期上尚未确认的报告失效（EXPIRED）；见面后同样失效。旧档期不能再产生有效的爽约处罚。
- 复核时工作人员看到双方的到达声明，但页面明确写着「本人手动声明，不是定位证据」。

### 4.3 自动限制规则（透明、保守）

只有「对方承认」或「工作人员确认」才算已确认爽约，按 30 天滚动窗口计数。**计数口径是确认时间**（对方承认或工作人员确认的时刻），
不是档期发生时间——沿用 V10 语义；7.1 起还要求这次确认对应一个明确的档期快照：

| 30 天内已确认爽约次数 | 结果 |
|---|---|
| 第 1 次 | 仅提醒（「我的限制」里显示提醒） |
| 第 2 次 | 限制预约新订单 24 小时 |
| 第 3 次及以上 | 限制预约新订单 72 小时 |

单方 PENDING、DISPUTED、REJECTED、EXPIRED 都不计数；一份报告至多触发一次（唯一索引）；到期自动结束，记录保留用于审计；
不限制浏览、查看订单和完成已有订单；申诉成功撤销未到期的限制，并把那次确认改为 REJECTED（不再计数），写入审计；
以它为依据、仍未到期的其他自动限制会被重算（只缩短或撤销，见第 13.2 节）。

## 5. 用户限制与统一检查点

`RestrictionGuard` 是唯一的检查点，服务端所有相关入口都调用它（前端隐藏按钮只是体验）：

| 范围 | 禁止 | 不影响 |
|---|---|---|
| BOOKING | 创建新订单 | 已有订单的验货、确认、取消、消息；浏览 |
| PUBLISHING | 单件、打包、批量、草稿最终发布 | 保存草稿；下架已发布商品 |
| CIRCLE_CREATION | 新建圈子 | 已有圈子的管理；退出圈子 |

受限时返回 403，`data` 里有 `{code: RESTRICTED, scope, endsAt}`，提示写明解除时间与「可以在我的限制里申诉」。
检查时对用户行取 `FOR SHARE`，新建限制时取 `FOR NO KEY UPDATE`：「施加限制」与「下单」串行化，结果确定。

## 6. 平台工作人员

- 角色：`MODERATOR`、`SENIOR_MODERATOR`。强制归档圈子与超过 7 天的限制需要 SENIOR_MODERATOR；限制最长 30 天。
- 权限**每次请求**从 `staff_members` 读取（`active` 且学校等于本人所在学校），不写进 JWT、不信任任何客户端提交的角色；停用立即生效。
- 工作人员只能看到与处理本校案件；他校案件与不存在同为 404。非工作人员访问 `/v1/moderation/*` 一律 403。
- 一个案件只有一个最终结果：结案时锁案件行，要求仍是待处理 / 处理中；已被另一位工作人员领取的案件不能被他人结案（409）。
- 申诉必须由做出原处理之外的另一位工作人员决定（四眼原则）。
- 工作人员看到的目标摘要只有处理所需的最少字段：没有联系方式、确认码、账号、密码、Token 或会话全文；不显示举报人身份。
- 结案与申诉决定的响应带上本次请求的 `requestId`，界面显示为「操作编号」。

### 6.1 配置首个工作人员

表默认为空，不从公开注册接口创建，也没有默认账号。首个工作人员由运维按
[`campus-market-backend/docs/staff-runbook.md`](../campus-market-backend/docs/staff-runbook.md) 用受控 SQL 配置。

## 7. 举报与案件

- 举报目标：PRODUCT / USER / CIRCLE / COMMENT / MESSAGE / ORDER / NO_SHOW（后者只由报告人请求复核自己提交的爽约报告）。
- 只能举报自己看得到的目标：私密圈子、他人订单、他校或私密商品与不存在的 ID 返回同一个 404——举报接口不能用来枚举。
- 同一人对同一目标只保留一份举报（重复提交幂等）；同一目标的举报并入同一个未结案件。
- 消息举报只保存那一条消息的内容作快照，不复制整段会话，工作人员也读不到会话里的其他消息。
- 举报人在「我的举报」里只看到「已收到 / 处理中 / 已结束」与「平台已处理 / 未采取措施」；看不到具体动作、期限、工作人员或被举报人的处罚。
  案件进入申诉时，举报人看到的仍是原结果（不透露对方是否申诉）。
- 被举报的人只在「我的限制」里看到限制范围、期限、原因码与商品隐藏通知，看不到举报人。

治理动作：`HIDE_PRODUCT`、`RESTORE_PRODUCT`、`ARCHIVE_CIRCLE`、`RESTRICT_BOOKING`、`RESTRICT_PUBLISHING`、`RESTRICT_CIRCLE_CREATION`、
`CONFIRM_NO_SHOW`、`REJECT_NO_SHOW`、`NO_ACTION`（以及申诉决定 `ACCEPT_APPEAL / REJECT_APPEAL`）。没有资金赔付或真假鉴定。

被隐藏的商品：其他同学在列表、详情、feed、需求匹配里都看不到（与不存在相同），卖家本人看得到并看到「已被隐藏」提示，
已成立订单的对方仍能读取、完成交易。

## 8. 并发

`GovernanceConcurrencyIT` 在真实 PostgreSQL 上跑 10 组竞态（每组多轮），断言任何交错下都成立的结果：

1. 双方同时取消：都成功（幂等），只有一条取消记录、一条取消事件；
2. 取消与完成交易：恰好一个成功，取消记录存在当且仅当订单已取消，商品状态一致；
3. 改约与提交爽约报告：旧档期上不会留下有效报告；
4. 两人同时报告对方：两条 PENDING，没有处罚；
5. 工作人员确认与对方承认：恰好一个生效，至多一条自动限制，案件只结一次；
6. 工作人员限制与用户下单：不会有限制生效之后才成立的订单；
7. 限制到期与下单：成功的订单都在限制结束之后；
8. 工作人员强制归档与所有者归档：只归档一次、只有一条归档事件；
9. 两名工作人员同时处理一个案件：一个结果、一条动作、一条限制，另一人 409；
10. 申诉通过与限制到期：结论总是 ACCEPTED，撤销只会发生在到期之前。

加锁顺序固定为「订单 → 爽约报告 → 案件」，与「对方承认」的顺序一致，不会互相死锁；不依赖任何单机内存锁。

## 9. 性能

`GovernancePerformanceIT`：11 所学校，10 万取消记录、5 万举报、1 万案件、10 万治理动作、5 万限制、2 万已确认爽约。
用生产 Mapper SQL 执行 `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`，只断言计划形状与语句条数：

| 查询 | 计划 |
|---|---|
| 工作人员待处理列表 / 计数 | `moderation_cases_queue`（学校在索引前缀，按页取回） |
| 申诉列表 | `moderation_appeals_queue` |
| 我的举报 | `moderation_reports_mine` + 案件主键 |
| 我的限制 | `user_restrictions_mine`（有计划证据才加：已撤销 / 已到期的也要列出，部分索引覆盖不到） |
| 当前有效限制 | `user_restrictions_active` |
| 30 天爽约计数 | `order_no_show_reports_confirmed`（Index Only Scan） |
| 本人取消记录 | `order_cancellations_actor` |
| 目标的案件 / 案件的举报与动作 | `moderation_cases_target`、`moderation_reports_case`、`moderation_actions_case` |
| 消息举报目标 | `messages_pkey`，不读会话里的其他消息 |

案件列表的语句条数与页大小无关；案件详情的语句条数与举报、动作数量无关。

## 10. 隐私边界

- 被举报者不知道举报人；普通用户看不到工作人员身份（界面只写「平台工作人员」）。
- 工作人员不能跨校，不能获取确认码、密码、Token、联系方式或会话全文。
- 举报、单方爽约报告、限制都不进入公开资料或公共履历。
- 日志只有方法、路径、状态、耗时、requestId：没有消息正文、确认码、Token 或邀请码（`ModerationIT` 4 用 CapturedOutput 验证）。
- 未知字段一律 400；所有错误响应带 requestId。

## 11. 前端

- 用户侧：商品 / 留言 / 私信 / 圈子的举报对话框；订单流程页的爽约报告（承认前二次说明后果）；我的订单的取消对话框；
  「我的举报」「我的限制」（到期时间写出具体时间与还剩多久，状态用文字而不只靠颜色；每条可申诉一次）。
- 工作人员：`/moderation`（案件列表与筛选）、`/moderation/cases/:id`（详情、领取、结案，高风险动作二次确认写明影响与到期时间，
  结果显示操作编号）、`/moderation/appeals`。独立懒加载；非工作人员看不到入口，直接访问后端 403。
- 离线演示：Mock 构建的「个人资料」里有一个「设为演示工作人员」开关（`DemoStaffSwitch`），只在 `VITE_API_MODE=mock` 时懒加载；
  REST 构建里这段代码被常量折叠删掉，`check-bundles` 用 `demo-staff-switch` 标记验证。演示种子里没有预置工作人员。
- Mock schema v10：`cancellationRecords / noShowReports / staffMembers / moderationReports / moderationCases / moderationActions /
  moderationAppeals / userRestrictions / campusSchools`；v1～v9 均可升级，不伪造任何治理记录，更高版本不降级，损坏记录逐条隔离。

## 12. 已知限制

- 注册时的学校由用户自己选择的校区决定，平台没有校园邮箱或学籍核验；同一个人可以在另一所学校注册新账号。
- 爽约只能在档期结束后 7 天内报告；无人回应、也没有请求复核的 PENDING 报告会一直保持 PENDING（不计数）。
- ~~评论与私信没有「隐藏」动作~~（7.1E 已实现评论隐藏 / 恢复与单条私信隔离）；工作人员看不到被举报人的其他内容，需要时只能另立案件。
- 利益回避：一所学校只有一名工作人员、而案件或申诉与他有关时，案件保持待处理并明确告知用户，直到再配置一名工作人员（不会被自动驳回）。
  「本校暂时没有可以回避的工作人员」这一状态本身会让举报人推测被举报人可能是工作人员。
- 第一次已确认的爽约（只提醒、没有限制）如果是对方自行承认的，没有可申诉的处理；工作人员确认的那次可以申诉。
- V11 之前没有结束时间的原始预约不能认定爽约，需要双方先通过改约确认一个完整档期；这是刻意的取舍。
- 限制期间的通知只在站内「我的限制」里；没有短信、邮件或推送。
- axe 在 jsdom 中无法计算颜色对比度；键盘测试用焦点与按键事件模拟，自动化检查通过不等于 WCAG 合规。

## 13. 模块 7.1：治理规则收口

### 13.1 明确档期，不用推测处罚（7.1A）

- **审计**：V10 里 revision 0（卖家接受买家提交的原始预约）只有开始时间，爽约资格按「开始 + 1 小时」推算结束时间——这是推测，7.1 取消了它。
- **新预约**：下单时保存明确的开始与结束时间（`meetingEndsAtIso`）。下单页让买家选时长（默认 60 分钟，15～120 分钟），并实时显示完整时段；
  服务端校验结束晚于开始、时长 15～120 分钟、开始在 1 分钟后到 30 天内；不提交结束时间的旧客户端由服务端明确写入默认 60 分钟并返回。
  卖家在「接受预约」按钮旁看到同一个完整时段（按钮用 `aria-describedby` 关联这句说明）。
- **接受即冻结**：卖家接单（revision 0）或改约被接受（revision N）时，触发器 `orders_record_slot_agreement` 写入 `order_slot_agreements` 快照；
  `orders_slot_guard` 让订单上的时间 / 地点只能随版本号增加（即改约握手）变化；快照只增不改。
- **爽约只认快照**：可报告时间 = 快照结束 + 15 分钟；接口返回所依据的快照（`eligibility.slot`）。
- **旧订单不猜**：没有快照的原始预约返回 `NO_EXPLICIT_SLOT`，不能报告；已有的旧报告不能被承认（409）、工作人员没有「确认爽约」可选（硬发 400），
  直接写库确认也被触发器 `order_no_show_reports_slot_guard` 拒绝；只能驳回或失效。可以先通过改约握手确认一个完整的新档期（revision 1），之后按新快照判断。
  不伪造任何旧订单的结束时间。
- 「已到达」仍然只是本人声明，不作为处罚证据；工作人员复核页写明档期是否明确（`meeting.explicit`）。

### 13.2 自动限制重算（7.1B）

- 自动限制保存：`source = SYSTEM_RULE`、来源报告、`rule_version = NO_SHOW_V1`、决定时间 `decided_at`、依据 `user_restriction_basis`（每条依据的确认时间快照）。
  本人在「我的限制」里看到来源、规则版本、按确认时间列出的依据（被推翻的标明）与纠正记录；看不到任何他人身份。
- **申诉推翻一次确认**（申诉限制本身，或申诉工作人员确认爽约的那次处理）后，`RestrictionGuard.recomputeAfterOverturn` 重算以它为依据、仍未撤销的自动限制：
  - 已自然到期的：不改动，只保留原有审计；
  - 来源报告本身被推翻：撤销（`RULE_RECOMPUTED`）；
  - 否则按依据中仍处于已确认状态的次数重新套用**决定时的规则版本**：新结束时间 = 开始时间 + 新时长；
  - **只减轻或撤销**：新时长不少于原时长时保持原样；新结束时间已过则直接撤销；
  - 每次变化追加一条 `user_restriction_corrections`（原结束时间、新结束时间、剩余次数、原因报告、申诉、决定人），历史动作不删除；
  - 人工（CASE）限制不受影响；多条限制并存时统一检查点仍按仍然有效、结束最晚的那条判断。
- 数据库兜底：限制的结束时间只能由 SYSTEM_RULE 限制、按一条 SHORTENED 纠正记录、向更早的方向改；按重算撤销必须指向一条 REVOKED 纠正记录。
- 例：第 2、3 次确认分别产生 24 小时与 72 小时限制；第 2 次被申诉推翻 → 第 2 次的限制撤销、第 3 次的 72 小时缩短为 24 小时（剩余 2 次）。
  剩余只有 1 次时自动限制被撤销。
- 并发：申诉决定按「申诉 → 用户 → 限制 / 内容 → 报告」加锁，与「新确认」「下单检查」在用户行上串行化；两条针对同一用户的申诉同时决定也不会死锁
  （`GovernanceConcurrencyIT` 11、12）。

### 13.3 工作人员利益回避（7.1C）

- 判断在数据库：`staff_case_conflict(case, staff)`、`staff_appeal_conflict(appeal, staff)` 返回原因码（`SELF_TARGET`、`OWN_CONTENT`、`OWN_CONVERSATION`、
  `OWN_ORDER`、`OWN_REPORT`、`OWN_ACTION`），后端 `ConflictGuard` 在查看详情、领取、结案、立案、决定申诉前调用，冲突时 403 `CONFLICT_OF_INTEREST`；
  冲突的案件与申诉不进入本人的队列、不计入总数。界面只展示原因，不自行判断。
- 覆盖：以本人为目标；本人的商品 / 评论 / 私信 / 圈子；本人参与的订单与爽约报告；本人提交的举报；对本人做出的处理的申诉；本人在原案件做过处理；本人自己的申诉。
- 没有合适的工作人员：保持待处理；「我的举报」「我的限制」里的申诉显示「本校暂时没有可以回避利益冲突的工作人员……不会被自动驳回」。
- 自动限制（没有工作人员）的申诉：本校任何无利益冲突的工作人员都可以决定（报告人恰好是工作人员时由其他人决定）。
- 工作人员停用后下一个请求立即失权（权限每次从数据库读取）。

### 13.4 邀请幂等边界（7.1D）

- 固定契约：邀请**可用** = PENDING 且未过期；**原兑换者重放** = REDEEMED 且兑换人就是本人（网络重试、双击）；其余一律同一个 404（不存在、过期、撤销、被他人兑换、他校、圈子已归档）。
- 只有邀请本身满足规则之后才考虑「已在籍 → 200 且不消耗」；随机码不会因为用户在某个圈子里而得到 200。原兑换者退出后不能用旧码重新加入。
- 每次尝试都照常计入限流（没有降低）。

### 13.5 内容处置（7.1E）

- **评论隐藏 / 恢复**（`HIDE_COMMENT` / `RESTORE_COMMENT`）：只有本校有权工作人员；普通接口对任何人（包括作者）都不返回被隐藏的正文，
  其他人看到「该留言已被平台隐藏」，作者看到可申诉的提示；原文保留，正文不可改写、处置过的不能删除；动作追加审计；作者申诉由另一位工作人员决定，成功则恢复。
- **单条私信隔离**（`QUARANTINE_MESSAGE` / `RELEASE_MESSAGE`）：只针对被举报的那一条；会话双方都只看到占位提示、看不到正文；
  会话与其他消息照常、已有订单可以继续沟通；工作人员只在对应案件的举报快照里看到这一条的正文，不读取整段会话；发送者可以申诉。
- 只限制作者**不会**被当成已经处理了内容：限制不隐藏任何历史内容，需要处置内容时要执行对应的动作。
- 这四个动作同步写进了数据库 CHECK（V11）、接口、Mock、界面与本文档。
